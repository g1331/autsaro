# BUILD-004：构建时核对生成工程完整性

**状态：**review。**分支：**`feature/BUILD-004-build-integrity`。**基线：**`dad392b`。**依赖：**BUILD-003。**关联能力：**HOST-CAN-01。**类型：**产品构建流程风险修复。

## 范围与依据

CP/FO R24-11、无配置变体、Windows 主机虚拟 ECU 与 MinGW GCC；先用 11 位 Classical CAN 信号工程验证。工作台已经生成 `files.list` 和 `files.sha256`，但当前工作台构建会直接扫描 `src/*.c` 编译；生成后若文件被外部修改或添加，界面的构建状态仍可能显示为该配置的成果。本卡依照 07 号验收议题的输入—生成物—构建可追溯项目质量门处理这一风险，不新增 AUTOSAR 模块或规范行为。离线 `build.ps1` 仍供交付者自主构建；其运行不被本卡记录为工作台核验。

## 可观察结果与拒绝

1. 工作台构建前读取生成清单，核对文件名、所有列出的文件、摘要及额外文件；通过后才启动 GCC。构建后安装二进制前再次核对，来源变化则拒绝将构建标为成功，保留用于诊断的临时产物。
2. 正常生成的 CAN 工程仍可构建、链接及按独立位向量运行。修改生成 C、修改清单、增加额外 C 文件、删除列出文件时，构建拒绝，原生成目录内容不被改写且无正式 `ecu_host.exe`。
3. 仍拒绝覆盖已有二进制。此核对面向误改和构建结果归属，不是签名认证；同时有意修改文件与完整性记录的情况不作为防护声明。原生桌面若没有隔离环境则标为未验证。

## 验收

在 `core/tests/end_to_end.rs` 覆盖正常构建与上述关键拒绝路径；运行 `python scripts/workflow.py verify --scope all` 与 `check`，保存工具链、命令、输入、输出和限制。进入 `review` 后由新的 Agent 会话独立核对源码、测试及证据，再决定是否收口；本卡不升级 HOST-CAN-01 的六道证据门或支持声明。
