# Agent 开发与交接契约

本文件同时适用于 Codex、OMP 和其他能读写此仓库的 Agent。每次启动都以当前用户要求为先，随后核对 `git status`、最近提交、[产品地图](../../.scratch/autosar-platform/map.md)、[README](../../README.md)、[验收决定](../../.scratch/autosar-platform/issues/07-assurance-gates.md)、[`state.json`](state.json)及[工作流反馈](feedback/active.json)。任务记录是执行入口，不替代当前源码和运行结果。工具专属 skill/plugin 若存在，只能指向本文件，不能复制一套易漂移的规则。

## 请求模式与交接输出

- **“状态如何”：**只读核对仓库与状态记录，运行 `python scripts/workflow.py status`；说明能力、证据缺口、当前任务、阻断与推荐下一步。不要改文件、领取任务、构建或合并。
- **“推进开发”：**恢复唯一进行中的任务；没有时按下面的排序选一项可执行任务。一次处理一个主要切片，完成验证与交接。已有用户修改或其他 Agent 的工作不得覆盖。
- **指定目标：**先判断是否已由地图授权；能在既定范围内推进的部分直接执行。需要维护者作产品决定时，推荐一个方案并说明影响，不把普通技术判断退回维护者。
- **审查：**从任务、规范原文和源码独立判断；不能把开发 Agent 的总结当作证据。审查者不得修改被审查代码，发现问题则让任务回到进行中。
- **“复盘工作流”：**从近期任务、反馈与实际结果检查流程摩擦；只修改有证据支持的流程部分，执行下文的试运行与归档规则。

向维护者的最终交接固定回答：“这次新增的 ECU 可运行行为、现有能力的操作/交付改进或关闭的风险、可复现证据、失败或拒绝场景、仍未验证、下一项推荐、需要维护者决定的事”。分别说明运行能力与配套工作的进展；没有新运行行为时直说，不把任务卡完成数、代码行数、PDF 数或笼统的 AUTOSAR 完成百分比代替进度。

## 从目标到任务

每次领取新任务，先核对最近完成的任务实际改变了什么、当前 Classic 阶段还缺哪种可运行 ECU 行为，再从阶段路线和具体缺口选候选；上一张任务卡的“后续”是线索，不自动成为最高优先级。区分三类成果：新增或扩展生成 ECU 的可观察运行行为及其配置闭环；改进现有能力的工作台操作、构建或交付；补齐证据与审计。生成器中的运行代码也属于第一类，不能只按改动目录或任务标题分类。

按“未解决的仓库门禁失败或真实回归 → 明确阻断当前运行切片交付的用户流程/工程缺口 → 当前阶段的可运行能力增量 → 非阻断的操作与交付改进 → 为眼前实现或支持声明必需的证据调查”排序。阻断须指向具体切片和失败场景，不能仅因某个证据门仍是 `not_run`、某处体验还能改善，就无限推迟运行能力。现有地图中的 Classic 阶段可在对应出口证据齐备后继续；新版本、实机目标与 AP 仍按地图的决策边界办理。若无可执行任务，先从阶段出口和实际缺口建立一张有界任务卡；不能凭空宣布整个模块完成。任务过大时先做有来源、结论和后续任务的限时调查。

若最近连续两张已完成的主要开发任务都只改善现有能力的操作、构建、交付或证据，且未新增可运行 ECU 行为，下一张默认选当前阶段的运行行为切片，走配置/生成 → 构建 → 独立正反向运行验证的适用链路。已知严重缺陷、直接阻断该切片的事实或用户指定目标可以改变顺序；在任务卡中写明阻断证据、受阻的运行切片，以及解决后如何回到它。不得为凑数量做空壳模块，也不因这条排序规则降低现有能力的质量门。

审计可以发现并修复真实缺陷，但“审计卡完成”不等于用户获得新能力。审计收口后要把已发现的可实施缺口变成产品任务；同一阶段连续两张审计卡均未升级支持声明或交付用户可见结果时，下一项优先实施一个有可观察结果的产品切片，不再仅因其他能力仍有 `not_run` 门而继续排审计卡。只有已知严重缺陷、明确的支持声明前置证据或用户指定的审计目标可改变这个顺序，并在任务卡中说明理由。交接时分别报告产品源码/用户流程变化与审计认识，不能把文档页数或任务卡关闭数合并为“功能进度”。

任务须指定 CP/FO 版次、模块与配置子集、变体、目标/工具链、可观察结果、明确拒绝范围、依赖、准确规范条款或 MOD 对象、适用/不适用理由和验收场景。官方 PDF/ZIP 保持 Git 忽略；只记录可定位的出处，不复制大段标准文本。规范要求、项目质量门、主机专属行为分开标识。未解析但影响生成的配置必须拒绝，不能猜测或输出空壳。

## 开发、验证与审查

1. 在独立分支或工作树实施，记下基线提交。主工作区不干净时先确认归属并隔离；不要撤回不属于本任务的修改。保存中断或会话结束时，任务记录至少包含分支、已完成内容、失败原因和下一步，新 Agent 也须自行核对。
2. 沿适用的输入/保存 → Schema 与引用/语义 → 生成工件 → C99 编译链接 → 主机或目标行为 → 用户流程实现。对解析、生成和主机行为按仓库测试约定添加成功及关键拒绝测试。预期值从规范、模型或独立计算得到，不能由被测生成器反推。
3. Windows 新 PowerShell 会话首次运行 Cargo 或 `verify` 前，先核对 `VCPKG_ROOT`、`VCPKGRS_TRIPLET`、`LIBCLANG_PATH`；缺失时按 `README.md` 的本机依赖说明设置，独立审查会话也如此。按 README 安装固定版本的格式器与 UI 依赖后，用 `python scripts/workflow.py verify --scope all` 执行增量交付门；它检查源码空白、新改行格式、Python/C99 语法、UI ESLint、类型与构建、核心测试、桌面构建和 Rust Clippy 的 correctness/suspicious 类别。格式检查在进行中的任务上使用 `base_commit`；没有进行中任务时，未提交改动对比 `HEAD`，干净工作区复核上一提交时对比 `HEAD^`。核对更长的已提交范围时显式传 `python scripts/quality.py --base <基线提交>`。另运行 `python scripts/workflow.py verify --scope baseline` 查看受支持源码的全文件格式、Python/UI lint、全告警 Clippy、运行时 BSW/RTE 的部分 MISRA 扫描、需用 `--generated-dir <工程目录>` 指定的代表性生成 C 扫描及逐能力规范证据缺口；它汇总所有失败项，不能通过豁免旧债制造绿色。小改动可先运行 `--scope core`，最终交付仍按任务适用范围核对。记录提交、输入、工具链、命令、输出与失败路径。其他生成配置 C、完整 MISRA C:2012、适用模块 SWS、原生界面、指定 MCU 和第三方互操作若未完成，明确标为待审，不能被一次绿色构建或部分扫描代替。
4. 新能力、AUTOSAR 语义变化和支持声明升级须经过**新的 Agent 审查会话**，给审查者原任务及证据，不给开发结论作唯一依据。可用同一工具的新会话，也可换用另一工具；审查意见与修复结果写入证据。审查一致不等于规范符合性或实机证据。
5. 常规本地改动在主线干净、完整适用检查及复核通过后可合并到本地 `master`。合并冲突、测试失败、证据缺失、权限不足或支持范围不明时停止集成，保留分支并记录阻断。当前没有 Git remote；不得自行 push、创建 PR、发布或部署。重要产品语义、数据兼容和目标平台变更按现有授权边界处理。
6. 更新 [`state.json`](state.json)、任务卡和证据，再同步受影响的 README/阶段说明；只在产品决策变化时更新地图。任务“完成”可以得出“能力仍待审/不支持”的审计结论，不得放宽验收条件换取绿色状态。

## 全生命周期的状态边界

任务从 `proposed → ready → active → review → done`，也可进入 `blocked`；原因解除后回到 `ready` 或 `active`。最多一项 `active`。每项能力按**版次 × 配置/变体 × 目标/工具链**分别记录输入往返、工件闭包、构建、独立行为、用户流程和适用规范义务六道证据门。门的状态为 `not_run`、`failed`、`pending_review`、`passed`，或附理由的 `not_applicable`。README 的已实现主机行为不自动升级为内部已审支持。

[`state.json`](state.json)是跨会话索引：`capabilities` 记录每个组合的声明等级与证据门，`tasks` 记录任务卡、依赖、状态和证据文件。领取任务时填 `branch` 与 `base_commit`；进入 `review` 前建立 `docs/workflow/evidence/` 下的实际记录。审查通过后，审查记录填写 `reviewer`、ISO 日期及同目录证据路径。运行 `python scripts/workflow.py check` 可检查这些引用与状态转移的基本约束；运行 `python scripts/workflow.py status` 只读查看索引。`verify` 执行本地命令但**不会自动把门改成通过**，每门仍须记录输入、独立预期、实际输出、适用性与复核结论。

内部支持声明仅在全部适用门通过、证据可复现且审查记录存在时升级；实机目标再加指定板卡/工具链及目标行为证据。未来发布候选另检查干净构建、包内样例与说明、来源/许可、兼容范围和维护承诺，并由维护者授权实际发布。发布后缺陷作为高优先级任务重现、修复、回归并更新受影响的能力档案。任何 Agent 都不能从主机结果推断安全等级、量产可用或官方一致性。

## 工作流自身怎样改进

开发或交接中若遇到反复查找相同信息、任务边界不清、状态记录与实际不符、无效门禁、复核无法复现，或使用者看不懂交接，先判断是否是协作者可共同遇到、需要改变仓库流程的问题。符合时将**具体经过与代价**记入 [`feedback/active.json`](feedback/active.json)；同一根因追加观察，不为每次出现新建一条。单次本机进程占用、工具环境或临时路径等冲突，若影响验收就在任务证据中写清失败和替代验证，解决后不占用共享反馈队列；反复出现且有共同根因时再提炼为不含个人进程号、路径的共享问题。执行普通任务时顺手记录，不为填写反馈打断修复。严重的错误支持声明、数据风险或门禁绕过立即按缺陷处理，不等复盘。

每完成一项任务，核对反馈队列。满足任一条件就由 Agent 自行复盘：同一问题出现两次；自上次复盘又完成三张任务卡；严重反馈出现一次；试行流程改动后又完成两张任务卡。`python scripts/workflow.py status` 会只读显示触发原因。没有后台调度器；触发发生在下一次 Agent 被唤起并读取仓库时。若用户当前只要求“状态如何”，只报告复盘已到期，不修改文件。

复盘先区分一次性环境故障、实现缺陷、任务设计缺陷和流程缺陷。只调整能解释近期实例的一处流程，写明要解决的现象、改动文件、预期改善及失败时如何撤回。常规的任务卡模板、导航、交接格式和脚本易用性可自行改进；改动状态校验或证据门的脚本须由新的 Agent 会话独立复核。**不得借复盘降低证据门、改动产品地图的已定边界、扩大合并/发布权限或追认支持声明**。确需改变这些边界时，把反馈标为 `needs_decision`，给出推荐与影响，继续其他已授权工作。

流程改动先标为 `trial`，记录开始时已完成的任务 ID 和可观察的成功条件。后续至少两张任务卡检验同类情形；两张任务卡只触发检查，若都未触及该情形，继续试行，不能宣称问题已解决。问题消失且没有引入新摩擦，再从活跃队列移到 [`feedback/HISTORY.md`](feedback/HISTORY.md)，写清改动、观察和关闭理由。若仍出现或造成新问题，调整或撤回改动并重新试行；不得为了清空队列而删反馈。经确认是重复项或误报，也须在历史中留下简短理由。即使本次无需改动，也把复盘日期、检查的任务和结论记在历史，更新 `reviewed_done_task_ids`。复盘结果写进交接，但不以“优化工作流”替代当前产品任务。
