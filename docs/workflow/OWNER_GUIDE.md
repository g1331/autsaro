# 怎样用 Agent 推进这个仓库

在 Codex、OMP 或其他能访问本仓库的 Agent 中打开 `本仓库根目录`，直接用下面的自然语言指令启动工作。每次换工具或新开会话都可以重新说同一句；Agent 应从仓库恢复状态，不要求你复述上一次聊天或审查代码细节。

## 四种日常用法

| 你想做什么 | 直接对 Agent 说 | 你应该得到什么 |
| --- | --- | --- |
| 看进度 | “按仓库工作流检查当前状态，只读回答：现在能用什么、哪些还没验证、最大的阻断和推荐下一步。” | 一页中文摘要；不会改文件或合并代码。 |
| 放手推进 | “按仓库工作流推进下一项最有价值的任务。常规技术决定自行处理，完成验证、复核和交接后报告结果。” | 一项有边界的交付或具体的阻断结论，以及下一项任务。 |
| 给业务目标 | “我希望用户能够【你期望的操作和结果】。判断它与现有路线的关系，拆成可验收任务，推进已明确的部分。” | 推荐做法、用户可见的验收结果，以及只需你决定的重大取舍。 |
| 检查成果 | “按实际操作演示这次交付：成功与失败分别是什么样，另一人怎样从头复现，哪些声明仍没有证据？” | 演示步骤、实际结果、失败路径、证据和限制。 |
| 检查工作方式 | “看看最近的任务和工作流反馈；哪些问题重复了，哪些改动试行后确实有效？” | 具体摩擦点、已尝试的改动、下一步观察；需要你决定的边界另列。 |

如果你换用另一款 Agent，说：“先从仓库恢复当前任务和证据，再继续；不要依赖上一个 Agent 的聊天记录。”新 Agent 必须先核对 Git、任务和运行结果；发现记录与源码不符时，先报告并修正认识。

## 一次实际使用

以工作流刚建立时的状态为例，问“状态如何”，Agent 应指出 `AUDIT-001` 是当时下一张可领取的任务卡，并解释这次要弄清现有主机 CAN 能力的证据缺口。以后应以仓库的实时状态为准。接着说“推进开发”，它应完成选定任务所要求的调查、复现和独立复核，把结果写回仓库。审计发现未通过项也算明确进展：结论应说清哪项能力仍不能升级支持声明、缺少什么证据，以及下一张修复或审计任务是什么。

看交接时，你可以直接说“给我看一次能重现的成功和一次会被正确拒绝的情况”。如果 Agent 只报告“测试绿了”，让它指出输入、实际输出、证据文件和测试没有覆盖的范围。确认符合目标后，下次只需再说“推进开发”；无需自己给任务编号或逐条安排实现步骤。

如果报告“阻断”，让 Agent 说清阻断属于缺资料、环境故障、实现失败，还是需要你决定产品方向，并给出可执行的下一步。只有需要改变范围、成本、外部行为或发布决定时，你才需要作选择；技术上的排错由 Agent 继续处理。

Agent 在实际任务中遇到工作流不顺手的地方，会把具体经过记在[工作流反馈](feedback/active.json)。同一问题反复出现，或完成几项任务后，它会自行复盘并试行小改动；后续任务证明问题解决后，记录会移到[历史](feedback/HISTORY.md)。你也可以随时说“复盘工作流”。这项复盘不改变 AUTOSAR 功能是否通过验收的标准；涉及产品方向或授权边界时，Agent 会带着推荐方案请你决定。

## 你怎样判断是否满意

每次交接只需看五件事：

1. 用户新增了什么可用能力，或者关闭了哪个具体风险？
2. 有什么可复现的实际结果？测试通过只证明测试覆盖的范围。
3. 是否展示至少一条与任务相符的失败、拒绝或恢复路径？
4. 哪些尚未验证，尤其是主机、第三方互操作、指定芯片和对外发布的区别？
5. 下一项为什么比其他任务优先？

回答含糊时说：“先补齐可复现证据和限制说明，再向我报告。”你不需要判断函数实现、AUTOSAR 条款或测试代码是否正确；Agent 要把这些判断变成你能复现或审阅的事实。仓库状态也可由 Agent 运行 `python scripts/workflow.py status` 取得，但命令输出只是索引，仍须核对当前源码。

## 什么时候需要你决定

Agent 可以在已决定的 Classic R24-11 主机路线内选择任务、研究规范、修改代码、测试和完成通过门槛的常规本地集成。遇到新标准版次、真实 MCU/板卡、新的重大依赖或费用、重要兼容性和产品语义变化、对外 push/发布或超出既定范围的承诺时，应给出**一个推荐方案、理由、影响和仍可自行推进的工作**，再请你决定。

你可以随时说“暂停推进，只报告状态”或“这个方向不符合目标，改为【你的目标】”。这会改变后续任务选择；已有代码和证据仍须如实保留。当前流程由你主动唤起 Agent，没有后台执行器或自动通知；你不打开 Agent 时，仓库不会自行开发。
