# AP R25-11 生成—部署—运行边界：对照 CP R24-11

决策输入，不是 AP 实施方案或符合性判断。版本以官方 **AP R25-11** 为准；CP 一侧仅指本项目已确认的 [06 号生成器决策](../../project/archive/autosar-platform/issues/06-generator-architecture.md#答案)，**并非已验证的实现**。AP 的 PDF 页码均指文件印刷页码。现阶段只有主机软件、没有目标硬件或已选定的 AP 栈；以下“应验证”不声称已完成运行验证。

## 两条产物链不是同一运行模型

| 环节 | CP R24-11：本项目 06 号决策 | AP R25-11：规范所述产物/消费者 |
| --- | --- | --- |
| 输入和校验 | 本机空项目编辑或导入/导出 ARXML；R24-11 `AUTOSAR_00053.xsd`、引用与跨模块语义校验 → 版本化配置模型 → 确定性生成计划。XSD 不等于语义校验。 | 设计级 `AdaptiveApplicationSwComponentType`、`Executable`、数据类型、`ServiceInterface`（可混合 events/fields/methods/triggers）及端口；`ServiceInterface` 不能直接拿来为 CP 软件组件端口定型。[Manifest TPS §§3.1–3.2、4.2.1，pp.37、150–151](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_ManifestSpecification.pdf)。R25-11 对应 `AUTOSAR_00054`，不是 CP R24-11 的 `00053`。[Release Overview §1.4.5，p.12](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TR_ReleaseOverview.pdf)。 |
| 生成代码 | 面向虚拟 ECU/后续目标 MCU 输出模块 C99 实现与配置、RTE/集成代码、工程；目标 MCU 的 MCAL 接口与虚拟 CAN/时间接口分开；不由模板自行解释 ARXML。 | CM 工具根据服务接口模型生成**类型安全 C++** 请求方 proxy、提供方 skeleton；提供方从抽象 skeleton 派生实现。代理/骨架还要与实际 `ara::com` 语言绑定、通信绑定链接，不是把 CP 的 C99 RTE/BSW 改成 C++ 模板。[Platform Design §§8.3–8.4，pp.44–46](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_EXP_PlatformDesign.pdf)；[CM SWS §§7.1.1–7.1.2，pp.63–66](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_SWS_CommunicationManagement.pdf)。R25-11 AP 代码库最低 C++17。[Release Overview §1.5.4，p.13](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TR_ReleaseOverview.pdf)。 |
| 配置与分发 | 生成完整 C 工程、配置及目标适配，主机虚拟 ECU 闭环；06 号决策并未定义 AP manifest 或进程服务管理。 | **Application Design 不自动等于 Manifest**；设计和目标配置可相互引用。标准化 Manifest 序列化为 ARXML，但上传格式可由平台供应商选定且须保留语义；文件不必一件 manifest 对应一个物理文件。[Manifest TPS §§2.1–2.4，pp.32–35](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_ManifestSpecification.pdf)。Execution Manifest 配置 `Process`/状态相关启动、资源组、执行依赖；Machine Manifest 配置机器，TPS §11.3 的 `ProcessToMachineMapping` 指派模型明确要求在 Execution Manifest 中描述；Service Instance Manifest 配置接口/实例的传输绑定、端点、发现及 E2E/安全。TPS R25-11 还单列 Raw Data Stream Manifest 与 Software Distribution/`SoftwareCluster`，不能沿用 Platform Design §4.4 仅概括三类部署 manifest 的说法当作完备目录。[Manifest TPS §§2.5、10.1–10.3、11.1–11.3、13.1–13.3、16.1，pp.36、514–524、534–537、731–766、879](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_ManifestSpecification.pdf)。 |
| 启动与运行 | 虚拟 ECU 的 C99 运行实现和宿主模拟环境；将来硬件 MCAL 才承担目标硬件适配。 | 应用可含多个 `Executable`；一个 `Executable` 的模型化 `Process` 实例在运行时变成 OS 进程。二进制与 Execution、Service Instance Manifest 一起部署；EM 启动时读取可能已转换成平台私有格式的 processed manifests，按 Machine/Execution Manifest 启动、配置进程。机器 OS 初始化后，EM 是 **AP 的**初始进程（不排除平台外 OS init/驱动进程）；EM 自行进入 Startup Machine State，随后 State Management 决定状态，EM 执行状态变化；执行依赖规定同一 Function Group State 内的顺序，不会自行令进程启动，服务发现也不等于执行依赖。[EM SWS §§7.1.1–7.1.5、7.2、7.3.4.1、7.3.5、7.4.2.1，pp.26–29、39–43、47–48、55–57](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_SWS_ExecutionManagement.pdf)；[Platform Design §§4.1.4、6.2–6.3，pp.25、37–38](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_EXP_PlatformDesign.pdf)。 |
| OS 与通信 | 静态 C99 ECU 模块/RTE/集成链；不能以该运行实现充当 AP ARA 或 EM。 | OSI 要求多进程、独立地址空间/隔离与进程启动 EM；应用可调用 POSIX PSE51 的 C 接口及 C++ 标准库，FC 实现允许超出 PSE51；**PSE51 规范引用 C99 并不意味着 CP 的 C99 运行时可直接复用**。[OSI SWS §§7.1.2、8.1.1–8.1.2，pp.14–16、31–32](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_SWS_OperatingSystemInterface.pdf)。ARA 是功能集群面向 AA 的接口，不规定 FC 唯一进程拓扑；FC 可为库或服务，底层 IPC/FC 间私有接口由实现者决定。[Platform Design §§4.1.1、4.2.1–4.2.3，pp.19–20、26–28](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_EXP_PlatformDesign.pdf)。CM 路径支持本机/远程服务、SOME/IP、DDS、IPC 等绑定；服务发现可全静态旁路，或在运行时按配置发现。[CM SWS §§7.1–7.2.1.2，pp.63–75](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_SWS_CommunicationManagement.pdf)。 |

**[事实：互操作点，不是共同内核]** 官方设计明确 CP 与 AP 共存，均支持 SOME/IP。[Platform Design §3.4，pp.17–18](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_EXP_PlatformDesign.pdf)。但 CP 端用 ClientServer/SenderReceiver/Trigger 接口表达服务，AP 端用 `ServiceInterface`；系统级 `InterfaceMapping` 把 CP 端口元素映射到 AP 单一服务接口，方法、事件、字段需分别映射，CP 不因此获得 AP proxy/skeleton、ARA 或进程生命周期。[Manifest TPS §7.4–7.4.3，pp.431–434](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_ManifestSpecification.pdf)。AP SOME/IP 还需服务 ID/实例 ID、序列化、端点、发现时序、版本及错误响应一致；静态连接绕过服务发现及运行期服务版本检查。[Manifest TPS §§13.1–13.3.1，pp.731–766](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_ManifestSpecification.pdf)；[CM SWS §§7.2–7.2.1.2，pp.70–75，及文档变更记录 p.1 所记 R24-11 CP/AP SOME/IP error-response 互操作修正](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_SWS_CommunicationManagement.pdf)。**[推论]** “都支持 SOME/IP”只给协议层的潜在互通点，不能保证 CP R24-11 与 AP R25-11 已经端到端互通，更不能证明运行时或配置模型同构。

**[工程推论：可复用的只是有限通用工具]** 在保持各版本 XSD、模型语义、错误规则和生成后端独立的前提下，可重用本机 UI 框架、XML 解析/引用解析机制、可追溯诊断展示、确定性产物规划/构建调度这类*无平台语义*设施；若将来共享某些协议序列化工件，须由同一协议画像的互通测试证明，不先许诺。AP 必须另建服务设计→C++ 绑定、Manifest/SoftwareCluster→二进制部署、OS/EM/SM/CM→执行与传输的具体能力；“共用一个 CP/AP 版本化配置模型或 C99/C++ 目标运行库”不是现有事实。依据：CP 的 [06 号决策](../../project/archive/autosar-platform/issues/06-generator-architecture.md#答案) 与 [Release Overview §§1.3.3–1.3.4、1.5.1，pp.8–9、12](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TR_ReleaseOverview.pdf) 的 FO 互操作职责、AP FC 而非 CP 模块式标准化。

**[尚缺证据：统一架构不可逆前的主机样本]** CP 多项已承诺的主机虚拟 ECU 能力先各自稳定；之后选择明确的 AP R25-11 子集和可运行的目标 POSIX/ARA 栈与许可边界，在**软件主机**上制作真实服务接口/数据类型 → proxy/skeleton → application/provider+requester → Execution/Service Instance/Machine Manifest（含 ProcessToMachineMapping、端点与服务 ID）→ 二进制/processed manifest → EM 启动、SM 状态、CM 本机及 SOME/IP 回环的闭环。再以 CP R24-11 对端测试方法调用、事件、字段、服务发现或静态连接、版本/错误响应、重启恢复及负向配置；验证跨版本 ARXML 转换/拒绝行为和哪个通用设施真能共用。EM SWS 明说 Manifest 校验**预期由供应商工具承担**，运行时处理格式可以是平台私有；XSD 通过、生成 C++ 能编译、或只观察到网络包均非运行符合性证明。[EM SWS §7.1.3–7.1.5，pp.27–28](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_SWS_ExecutionManagement.pdf)；[CM SWS §§7.1、7.2.1.1–7.2.1.2，pp.63–65、73–75](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_SWS_CommunicationManagement.pdf)；[Manifest TPS §§2.3、7.4、11.3、13.2–13.3，pp.34–35、431–434、537、733–766](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_ManifestSpecification.pdf)。没有硬件就不要声称车载部署、时间/资源隔离或实车符合性已验证。本文未验证任何 AP 样本的真实生成、链接、安装或启动。
