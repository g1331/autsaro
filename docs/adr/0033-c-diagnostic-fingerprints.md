# 0033. C 分析处置按诊断指纹绑定

## 状态

[#609](https://github.com/g1331/autsaro/issues/609) 的不回退门使用诊断指纹，沿用
[ADR 0027](0027-misra-compliance-track.md) 的完整性要求和项目验收启用阶段。

## 指纹

一个指纹对应规则的一条诊断、一个位置和一个程序。格式 `c-diagnostic-fingerprints-v4`
以 UTF-8 规范 JSON（键排序、无分隔空白）计算 SHA-256，输入含以下内容。

- 检查器规则 ID、严重度、程序名、位置序号及整条诊断的有序位置列表。这保留关联位置与
  HostBatch／probe 的区别。
- 每个位置的交付相对路径或经验证的 SDK 头身份、定位的原始 token 在文件内的序号、该 token
  和它前后各至多八个 token，以及参与 TU 在此处发出的 GCC 展开 token。行列号只用于查找。
- 参与 TU 的相对路径和摘要。取同一程序内包含诊断任一位置的 GCC 或 Cppcheck 实际 TU。
  摘要覆盖 GCC `-E -dD` 的展开 token 和活动宏定义、Cppcheck 实际输入文件的原始拼写、
  逐 TU 定义与 SDK 头身份。原始拼写保留指令边界、宏名与左括号的邻接及实参中的空白，
  因此只在 `__CPPCHECK__` 分支中生效的变化也会使指纹失效。遇到行号宏、token 拼接、
  续行或 Cppcheck 读取的外部 SDK，保留物理空行。其余输入忽略纯空行，保留非空行和文件
  末尾换行状态。
- GCC 行标记用于定位，原始 checkout 根统一为相对路径，展开的 `__FILE__` 也去除项目根。
  Windows 路径键只忽略 ASCII 字母大小写，非 ASCII 字符按原样比较。SDK 或交付清单中
  多条路径命中同一键时拒绝绑定。摘要使用已登记的 SDK 身份及交付相对路径。
  Linux 路径保持大小写区分。
- 目标、编译参数及 include 顺序、编译器目标／版本和内置宏、检查器版本与源码 revision、
  实际 Cppcheck 二进制、GCC driver／cc1 的 SHA-256，以及 addon／库／模型和项目检查驱动
  的身份。即使自报版本相同，二进制不同也会使旧处置失效。

GCC 不为所有原始指令发出 C token。原始定位和 Cppcheck 工程输入仍覆盖这类报告。
同一参与 TU 中的其他源码或共用头变化也可能使指纹变化。v2 为跨 TU 规则绑定整程序。
八份迁移前回执中，每份有 308 至 311 个已处置的 R2.5 位置，另有 R2.3 和 R8.7。
v4 逐程序读取固定 addon 的全部 `.ctu-info`，按 `files.txt` 核对 TU 覆盖。先用原始
诊断位置识别实体，再按 `analyse_ctu_info` 使用的事实类型绑定所有同名贡献。
R2.3／5.6 用 typedef，R2.4／5.7 用 tag，R2.5 用宏与使用标记，R5.8／5.9 和
R8.5 至 8.7 用对应的标识符声明、定义或使用事实。
事实在独立 C 文件时绑定所属 TU，在头文件时绑定现有使用者的头文件拼写、GCC 展开、
宏定义和 SDK 身份。头文件消费者亦保留 Cppcheck 实际读取的主 TU 指令及到最后一个
include 为止的原始输入，覆盖 GCC 未启用的 `__CPPCHECK__` 分支。事实按规范序列排序并保留
重复次数，原诊断的关联位置保持原序。缺失或歧义的诊断证据阻断门禁。
[固定 addon 源码](https://github.com/cppcheck-opensource/cppcheck/blob/e73bf44c3e49686b7495fab352d03a6c6075516b/addons/misra.py)

## 门禁与证据

原始检查仍按目标与样本的完整配置分别运行。当前与基准生产器从各自编译器原始输出
生成 `diagnostic-fingerprints.json`，配对作业核对 raw 清单的工件摘要、原始分析摘要及
位置／程序覆盖，再按
八份作用域回执重算范围内差集。比较回执随 `gate.json` 输出，保留新增、消失、证据不足
和过期的登记。正式处置沿用原标准篇及批准证据。
基准工件满足原有复用条件且附带有效指纹时可复用该清单，并重新绑定本次重算的原始摘要。
缺少指纹清单的候选工件回到基准现场扫描。

[SARIF 2.1.0 §3.27.17 和 §3.27.24](https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html)
对应 `partialFingerprints.autsaroDiagnostic/v4` 和 `baselineState`。转换器先核对
`gate.json` 中的双侧摘要和诊断／位置／程序覆盖，再按第一父树标注 `new` 或
`unchanged`。摘要或覆盖无效时仅导出原始诊断。

SARIF 按目标、样本和程序使用独立 run 与类别。每个 run 最多 5,000 条，超出时按原顺序
分段并赋予独立类别，避免 GitHub 截断结果。HostBatch 沿用原样本类别，probe 使用独立类别。
CI 每个样本一个 SARIF 文件。GitHub 每文件最多 20 个 run，两个程序各固定 10 个类别槽位，
每个程序最多发布 50,000 条。完整扫描后未使用的槽位发空 run，使告警数量回落时也能更新
以前使用的溢出类别。超过容量时转换明确失败，原始证据仍由流水线保留。
程序任一侧有未绑定结果时，该程序的 run
省略 `baselineState`，可用的指纹照常导出。消失及不能绑定的项留在比较回执。GitHub
告警匹配由平台处理，仓库门禁直接比较本次分析回执。
[GitHub SARIF 限额](https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support#sarif-data-limits)

以目标／样本索引处置。每条指纹绑定当前解析得到的处置类别、实体、技术依据和批准引用。
GRP 重分类继续按实际归属和规则判定。现有 R17.3 C99 适用性结论按精确指纹登记。
Mandatory 偏离禁止登记。PR 阻断范围内未处置
的新增诊断、失效处置和不完整的证据。诊断修复后，删除其绑定即可。基准仍是实际测试提交的
第一父提交，两侧用同一分析入口；缺失、失败、不可比、重复或漏扫仍阻断。主线和发版沿用
完整输入身份核验，并在每个样本的 gate 回执保留两树完整原始分析清单。发行构建先解析
目标提交，再为同一提交运行八样本严格分析。严格项目验收
仍独立复核人工、采用代码、正式偏离及无警告位置的义务。

配对作业从自身 checkout 和已核验 seal 的工程复算输入、配置、生成器和规则身份。分析器、
编译器、Python 和 runner 等生产端字段随整份清单绑定独立上传的生产回执，严格汇总核对
该绑定。发行入口先验证选定提交支持严格分析并具备完整登记，再启动平台矩阵。

## PR 中的 R10.3／R10.4 定向复算

Linux 配对作业对第一父树和测试树中规则、程序、位置和原报告唯一对应的未处置新增项复算。
两侧使用各自生产清单绑定的编译数据库和同一 Cppcheck 二进制、MISRA addon、库及平台模型。
同一树内两个程序的 TU 命令一致时只执行一次。当前覆盖主源文件中的直接整型操作数，
且该 TU 的输入变化限于一个局部对象改名或头文件中不透明结构体指针声明的 tag 改名。
检查器须在每个配置的同一位置再次报告该规则。局部对象的改名位置须全部解析到同一条局部声明。
两侧的类型、值、宏、声明及运算符证据相等才从 PR 新增项中移除，双树观察值随 gate 回执保留。

原始 v4 指纹和逐项处置照常核验。任一侧有登记的条目、复合表达式、缺少原编译数据库或
检查器证据的条目沿用精确比较。Windows 配对作业在 Linux 上运行，继续使用其原生扫描的
精确指纹。主线和发版的严格模式只消费原始指纹。

## Windows 分析器构建身份

`windows-2025-vs2026` 池的 `20261103.298.1` 与 `20261116.315.1` 以 MSVC 19.51、19.52
产生了不同机器码。当前模型为每个已实扫的 prepare 镜像登记精确的 EXE SHA-256。prepare
对冷构建和缓存恢复做同一验证，同一运行的两树都消费该 EXE。处置文件按实际 EXE SHA-256
选择，每个版本均来自其四份原始实扫，禁止用另一版本重新填入哈希来沿用结论。
遇到新镜像或二进制变化，先完成真实扫描和处置比对，再更新该身份及登记。

固定 MinGW 构建可减小对宿主 MSVC 的依赖。切换仍需要证明 C++ 编译工具、链接工具和
运行库可复现，并用新 EXE 重扫四份样本。当前采用两套已核验的镜像／EXE 组合。
[镜像差异证据](https://github.com/g1331/autsaro/issues/606#issuecomment-7031484360)

[ADR 0006](0006-builtin-rules-without-official-archives.md) 的规则与输入变化使相关确认失效
原则沿用。[ADR 0025](0025-misra-layered-scope.md) 的作用域、GRP、正式批准和 Mandatory
禁止偏离沿用。[ADR 0026](0026-project-source-acceptance-preserves-raw-analysis.md) 的原始
诊断、退出码、`passed`、221 项评估和 `completeCompliance` 均保持原义。项目验收的启用阶段
沿用 ADR 0027，[ADR 0032](0032-pr-checks-and-master-validation.md) 规定的扫描矩阵和聚合入口
继续使用。交付源码、生成接口和 ABI 无变化。

## 取舍与切换验证

使用绝对行号会随搬行失效。只绑定源代码行会漏掉远处定义，同文位置的删除和新增也会
相抵。把完整工程摘要放进每条指纹会重现整组重绑。将当前扫描结果自动写成批准会丢失
原始批准的适用条件。采用实际展开与程序证据，以变异分别核对周边代码、共享头宏和
typedef、编译配置、规则版本、移动行和无关 TU。迁移必须逐样本逐位置核对处置状态、类别、
理由、批准引用与程序归属，两次独立模块变更再核对先后合并时的有效记录。
