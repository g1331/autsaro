# 0017. 条款处置写在测试与 standards.md，核算结果现算

## 背景

模块整改要求核对所涉模块在所选配置下的全部适用义务，但此前无法回答“某模块还有哪些官方条款没有处置”：`standards.md` §5 只列已定位条款，测试几乎不引用编号。从 PDF 抓取编号不可靠，CanIf PDF 能找到 389 个编号，其中约 30 个来自变更历史中已删除的条款，DRAFT 状态也只出现在正文里。

官方 `AUTOSAR_CP_MOD_SpecificationsARXML.zip`（CP 清单内）以 `TRACE`／`TRACEABLE-TABLE` 元素逐条给出每份文档的条款，并用 `LIFE-CYCLE-INFO` 标注 draft／obsolete。CanIf 共 493 条：`SWS_CANIF_` 359、`ECUC_CanIf_` 119、`SWS_CANIF_CONSTR_` 14、`SWS_CANIF_NA_` 1。

AGENTS.md 禁止额外生成报告、矩阵或台账。若手工维护逐条矩阵，它会与测试和代码脱节，正是该规则要避免的情况。

## 决策

1. 条款清单以 SpecificationsARXML 中对应文档的 `TRACE`／`TRACEABLE-TABLE` 为准，包括 `ECUC_`、`CONSTR`、`NA` 前缀的条目；draft／obsolete 条目同样列出并标注。档案登记在 `core/resources/official.json`，由 `fetch-official` 下载校验。
2. 处置结论写在两处，并用显式标记区分类别。只有紧跟标记的编号才计入处置；顺带提及的编号，以及 §5 中尚未整改的“已定位”记录，都不计入：
   - **已验证**：验证该条款的测试在注释中写 `Verifies: <编号>`，适用于任何语言的测试文件，包括 `core/tests/fixtures` 下的 C consumer；
   - **已核对**：不靠测试、通过审阅确认的条款（如头文件内容规则），在 `standards.md` 模块行写 `已核对（<核对方式>）：<编号>`；
   - **不适用**：在 `standards.md` 模块行写 `不适用（<理由>）：<编号>`，例如所选配置未启用的可选功能；
   - **差距**：在 `standards.md` 模块行写 `差距 #<Issue>：<编号>`。
   一个标记后可列多个完整编号，用 `、`、`,`、`／` 或空格分隔，编号可加反引号；逗号后可在下一注释行继续。同前缀的后续编号可用 `／`、`,` 续写，或用 `–` 表示范围。编号嵌在标识符中（如测试函数名）不计入。分组处置可以写成表格，但每个编号单元格须以标记开头。
3. `python -m autosar_tooling requirements <文档>` 每次从档案和上述来源现算：各类别（已验证、已核对、不适用、差距）的条目数、未处置的条目，以及失效的编号引用。失效引用是指带有该文档的前缀、但 R24-11 中没有的编号，无论是否带标记都要检查。核算结果不提交、不写文件。
4. 这不属于 AGENTS.md 禁止的台账：处置结论位于验证或说明它的地方，随测试和文档一起审阅；核算结果随时可从这些来源重算。禁止的仍是脱离测试与代码另外维护的报告、矩阵和台账。
5. 不进入必需检查（档案须在运行时下载）。模块整改完成时，该模块文档的两类清单都须为零，并在 `acceptance.yml` 中把该文档改为完整检查；其余已被引用的文档只检查失效引用。

## 后果

- 工具只核算引用是否存在，不判断处置是否正确：测试引用了编号却没有验证该条款，或不适用理由不成立，仍须靠审阅发现。
- `Verifies:` 注释和 `standards.md` 中的标记就是处置依据，删除或改写它们时要按同样标准审阅。
- `standards.md` 模块行会随整改变长；同类条款可按组或范围处置，不必逐条写理由。未按新写法整改的行沿用原记录，其中的编号（无论简写或完整）都不计入处置。
- 档案约 243 MB，与其他官方档案共用 Actions 缓存。

已接受（2026-10-13），已实施（[#113](https://github.com/g1331/autsaro/issues/113)）。
