# 0017. 条款处置写在测试与 standards.md，核算结果现算

## 背景

模块整改要求核对所涉模块在所选配置下的全部适用义务，但此前无法回答“某模块还有哪些官方条款没有处置”：`standards.md` §5 只列已定位条款，测试几乎不引用编号。从 PDF 抓取编号不可靠，CanIf PDF 能找到 389 个编号，其中约 30 个来自变更历史中已删除的条款，DRAFT 状态也只出现在正文里。

官方 `AUTOSAR_CP_MOD_SpecificationsARXML.zip`（CP 清单内）以 `TRACE`／`TRACEABLE-TABLE` 元素逐条给出每份文档的条款，并用 `LIFE-CYCLE-INFO` 标注 draft／obsolete。CanIf 共 493 条：`SWS_CANIF_` 359、`ECUC_CanIf_` 119、`SWS_CANIF_CONSTR_` 14、`SWS_CANIF_NA_` 1。

AGENTS.md 禁止额外生成报告、矩阵或台账。若手工维护逐条矩阵，它会与测试和代码脱节，正是该规则要避免的情况。

## 决策

1. 条款清单以 SpecificationsARXML 中对应文档的 `TRACE`／`TRACEABLE-TABLE` 为准，包括 `ECUC_`、`CONSTR`、`NA` 前缀的条目；draft／obsolete 条目同样列出并标注。档案登记在 `core/resources/official.json`，由 `fetch-official` 下载校验。
2. 处置结论写在两处，并用显式标记区分类别。只有紧跟标记的编号才计入处置；顺带提及的编号，以及 §5 中尚未整改的“已定位”记录，都不计入。标记只在对应的来源中有效：测试用 `Verifies:`／`Rejects:`，`standards.md` 用其余标记。写在另一处的标记不计入，因此测试注释不能宣布条款不适用，文档也不能声称已验证：
   - **已验证**：验证该条款的测试在注释中写 `Verifies: <编号>`，适用于任何语言的测试文件，包括 `core/tests/fixtures` 下的 C consumer；
   - **已核对**：不靠测试、通过审阅确认的条款（如头文件内容规则），在 `standards.md` 模块行写 `已核对（<核对方式>）：<编号>`；
   - **不适用（配置）**：条款只在某项配置下适用，而产品不支持该配置。写 `不适用（配置：<ECUC 参数编号>[=<值>]…）：<编号>`。理由中列出的每个 ECUC 参数，都须有测试证明产品在生成前拒绝该配置，并在测试注释中写 `Rejects: <ECUC 参数编号>`。缺少 `Rejects:`，或理由中没有 ECUC 参数，核算即失败。以后若开始支持该配置，拒绝测试会失败，迫使重新处置；
   - **不适用（归属）**：义务属于其他模块、集成方或配置工具，写 `不适用（归属：<承担者>）：<编号>`，不要求测试；
   - **差距**：在 `standards.md` 模块行写 `差距 #<Issue>：<编号>`。
   一个标记后可列多个完整编号，用 `、`、`,`、`／` 或空格分隔，编号可加反引号；逗号后可在下一注释行继续。同前缀的后续编号可用 `／`、`,` 续写，或用 `–` 表示范围。编号嵌在标识符中（如测试函数名）不计入。分组处置可以写成表格，但每个编号单元格须以标记开头。
3. `python -m autosar_tooling requirements <文档>` 每次从档案和上述来源现算：各类别（已验证、已核对、不适用（配置）、不适用（归属）、差距）的条目数、未处置的条目、缺少 `Rejects:` 测试的配置条件，以及失效的编号引用。失效引用是指带有该文档的前缀、但 R24-11 中没有的编号，无论是否带标记都要检查。核算结果不提交、不写文件。
4. 这不属于 AGENTS.md 禁止的台账：处置结论位于验证或说明它的地方，随测试和文档一起审阅；核算结果随时可从这些来源重算。禁止的仍是脱离测试与代码另外维护的报告、矩阵和台账。
5. 模块整改完成时，该模块文档的未处置条目、缺少拒绝测试的配置条件与失效引用都须为零，并用 `requirements --update <文档>` 生成该文档的编号清单，提交到 `core/resources/requirements/<文档>.json`。清单只含条目编号与生命周期状态、其他文档使用同一前缀的编号（判断失效引用用）和来源档案的 SHA-256，不含规范原文。提交清单即把该文档登记为完整检查：必需检查的 `quality` 任务运行不带文档参数的 `requirements`，按每份清单完整核算，不下载档案；清单记录的档案哈希与 `official.json` 不一致即失败。`acceptance.yml` 从官方档案对每份清单所属文档完整核算，并核对清单与档案一致；其余已被引用的文档只检查失效引用。
6. **通用文档按模块处置。** `SWS_BSWGeneral` 的条款对每个 BSW 模块各自成立，按编号去重会让一个模块的证据替所有模块处置。因此这份文档的标记在冒号前带模块限定：`Verifies[<Mip>]:`、`已核对（<核对方式>）[<Mip>]：`、`不适用（配置：…）[<Mip>]：`、`不适用（归属：<承担者>）[<Mip>]：`、`差距 #<Issue>[<Mip>]：`，`<Mip>` 是模块缩写（如 `CanIf`）。核算某个模块时，只计入限定为该模块或 `[*]` 的标记；其他模块的标记和不带限定的标记都不计入。
   - **全局检查**：可机械检查的通用义务（如实现源包含 `<Mip>_MemMap.h`、文件命名、版本宏）可以由一项覆盖全部已交付模块的检查处置，写 `Verifies[*]:`，对每个模块都计入。该检查的模块集合须取自实际交付（如所有权清单或 `integration.json`），不能写成手列的部分模块；这一点和 `Verifies:` 本身一样由审阅保证。对所有模块都成立的核对或归属结论也可以写 `[*]`。
   - **核算与登记**：`requirements SWS_BSWGeneral --module <Mip>` 核算一个模块。模块整改完成时，除本模块文档外，该模块在 `SWS_BSWGeneral` 下的未处置条目、缺少拒绝测试的配置条件与失效引用也须为零，并用 `requirements --update SWS_BSWGeneral --module <Mip>` 把模块登记到该文档的清单（清单多一个 `modules` 列表）。必需检查和 `acceptance.yml` 对清单登记的每个模块分别完整核算；不带 `--module` 时，`--stale-only` 只检查失效引用，其他情形核算已登记的模块，没有登记时报错。第一个模块登记后，`SWS_BSWGeneral` 从 `STALE_ONLY` 移除。
   - 模块文档的标记不需要限定，写了限定也按原样计入。

## 后果

- 工具核算标记是否存在，以及配置条件是否有拒绝测试；处置本身是否正确，它不判断。例如测试写了 `Verifies:` 却没有验证该条款，或归属理由不成立，仍须靠审阅发现。
- `Verifies:` 注释和 `standards.md` 中的标记就是处置依据，删除或改写它们时要按同样标准审阅。
- `standards.md` 模块行会随整改变长；同类条款可按组或范围处置，不必逐条写理由。未按新写法整改的行沿用原记录，其中的编号（无论简写或完整）都不计入处置。
- 档案约 243 MB，与其他官方档案共用 Actions 缓存；必需检查只读取提交的清单。
- 清单是官方条目的编号索引，不记录处置：处置仍只写在测试与 `standards.md` 中。更换档案版本时，须重新生成全部清单并重新核算。
- 通用条款的处置按模块数量增长；共同的结论用 `[*]` 一次写出，只有模块间确有差别的条目才逐模块写。一项全局检查替所有模块处置，因此它漏掉某个已交付模块就会漏掉该模块的义务，审阅时须核对其模块来源。
