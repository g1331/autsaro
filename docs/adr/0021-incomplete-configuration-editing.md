# 0021. 自动补齐必需结构，允许不完整配置应用与保存

## 背景

新建模块或容器只插入空实例，定义校验随即报告必需子项不足；编辑事务拒绝新出现的定义错误，使使用者无法逐项补齐配置。[#255](https://github.com/g1331/autsaro/issues/255) 中使用者于 2026-10-17 决定允许这一中间状态，并在创建时补齐可确定的内容。此决定补充 [ADR 0020](0020-module-container-editing-model.md) 的单字段编辑模型。

## 决定

- 所有内置与已接纳扩展定义共用同一创建路径。新建模块或容器时，按定义下限递归创建必需子容器，以定义短名命名；同一定义需要多个实例时，从第二个起追加 `_1`、`_2` 等序号。必需参数有声明默认值时显式写入，按下限写足数量；无默认值的参数保持缺失，不编造值或引用目标。可选项不自动实例化。
- 自动补齐属于原创建事务，预览包含整个新增子树；任一拒绝不发布部分结构。已有实例不因编辑其他字段而自动补齐，不改写导入字节。
- 多重性下限不足使用独立诊断 `MULTIPLICITY_LOWER`，保持 Error 严重度、对象定位与问题列表展示，但不拒绝应用或保存。选择容器尚无分支也是下限不足，不擅自选择可选分支；选择多个分支仍拒绝。
- 上限、值、类型、引用与 schema 错误继续按既有安全编辑规则拒绝事务；既有无关 definition 错误仍采用见证比较，允许安全修复。保存保持源安全、schema、原字节及预览 revision 保护。
- 下限消息写明对象、定义短名、至少数量与现有数量；原始描述符、约束及反例保留在详情，不塞入消息摘要。
- 编辑接纳不改变计划与生成门槛。计划重新校验实际消费对象，Error 阻断其计划和生成；未被当前目标消费的保留对象沿用原有隔离边界。补齐必需值后重新校验和规划。

## 后果

使用者可以先创建、应用和保存，再逐个填写缺失参数。默认值成为新实例的显式配置；导入或已有对象的缺省显示不等于显式值。无需新的 IPC、界面组件或按模块维护创建规则。生成器、C ABI、运行时资产与第三方身份不变。

## 状态

已接受（2026-10-17，依据 [#255](https://github.com/g1331/autsaro/issues/255) 的使用者决定）。
