# 路线图

本文记录产品方向、近期顺序、依赖与仍然有效的需求约束。具体任务与状态在 GitHub Issues 和 Milestones 中跟踪；架构约束见 [architecture/](../architecture/README.md)，重要决定见 [adr/](../adr/)。R-ID 与 Epic 编号只是规划标识，不进入代码、测试或产品文件名。

## 产品目的

Autsaro 交付自有 AUTOSAR Classic 基础软件栈，以及配置、校验和代码生成工作台：使用者从新建或导入的多文件 ARXML 出发，安全编辑、校验并生成可独立交接、构建和复验的 ECU 工程。产品维护通用 BSW，按工程生成配置、RTE／应用接口和目标集成文件；车辆功能算法由使用者提供。优先扩大[主机功能与工程能力](reference-ecu.md)，以已定义的功能广度为最低基线，发展运行、仿真与可视化，再按目标条件接入真实 MCU；R10 可以后移（[ADR 0022](../adr/0022-reference-ecu-before-mcu.md)）。用户、定位、品牌与产品原则见 [PRODUCT.zh-CN.md](../../PRODUCT.zh-CN.md)。

## 当前交付范围

已交付能力、使用流程和支持表见 [README](../../README.zh-CN.md#当前支持) 与 [运行时支持范围](../../runtime/README.md)。路线判断需要的要点：

- **配置工作台（原 R5，已完成）：** 内置版本化校验规则和自有模块定义；新建／模板／导入、对象导航、定义驱动编辑、引用、批量修改、安全保存与重开、源码预览与用户代码保护。正常配置不需要官方 XSD／MOD、编译器或源码 checkout。
- **多组件应用与调度（原 R6 首批，已完成）：** SWC 类型／实例、显式 S/R 与同步 C/S 连接、runnable／事件与任务映射，生成一致的 RTE／SchM、应用接口与 OS 配置，按组件保护用户源码并独立交接。
- **OS 路线（已定，不再重选）：** 固定 FreeRTOS 内核＋自有 AUTOSAR OS 语义＋有限单核策略扩展，目标单核 SC1；受控 Win64 主机已有 SC1 行为与独立交接的复验记录。Trampoline／ATK2 仅作参考和备选。
- **通信与诊断：** 11 位 Classical CAN 信号链、有界物理 DoCAN、Dcm 会话（0x10）、TesterPresent（0x3E）与 DID 读取（0x22）。DTC、写 DID、安全访问、例程与持久存储随旧链路删除，主线以 NRC 0x11 拒绝，由 R7 在主线上重新实现。

明确不支持或未验证：

- 真实 MCU、硬实时、功能安全、官方一致性认证、完整 MISRA 结论、第三方互操作；macOS 原生构建与 IPC。
- ComM／Nm／CanNm／CanSM 网络管理（尚无运行模块与 ECUC 闭包）；29 位 ID、CAN FD、多通道。
- 未选的多组件扩展：队列、模式、异步 C/S、多实例；多核。
- 其他 AUTOSAR 版次（R25-11 仅作后续升级参考）、Adaptive Platform、学习层。
- 主机行为、内部已审支持、实机支持与公开发布是四种不同声明，不能互相推定。

## 近期顺序

**Epic 9 出口 → R11 → R7／R18 → R8 → R9／R14 → Epic 10 主机累计验收。**

R30 的[主机运行、仿真与可视化](host-simulation.md)随上述阶段发展，基础闭环进入主机累计验收，深入能力继续演进。**R10 是主机出口后可独立启动的真实目标接入，可以晚于更多功能和仿真增量；没有预设上板截止日期。** 板卡／工具链调查可提前，不阻塞主机功能扩展。

MCU 前最低范围见[参考工程要求](reference-ecu.md)，包括已调查的参数／接口、OS／RTE、项目／变体、输入适配、受管生成和扩展对象。共享契约先于消费者固定，能力随对应阶段交付，不能只挑最小示例需要的功能，也不能留给 Epic 10 或 R10 补实现。已完成阶段不重开，规划不作为支持声明。

### 1. Epic 9：运行时、生成 C 与开发工程体系整顿（进行中）

任务、共同规则与执行清单见 [#30](https://github.com/g1331/autsaro/issues/30) 及同名 Milestone。

先收敛出一条生成主线，再在主线上完成标准与 MISRA 整改（依据 2026-10-11 变更决定，取代原“三族分别整改”）。

**新基线（先行，按序推进，每步合并后 master 保持绿色）：**

1. 主线接管单 SWC 工程：新生成工程全部走现多组件主线，单组件即 SWC 数为 1；风险最高，先用最小单 SWC 正反例和内置模板端到端验证。
2. 主线拥有全部 BSW 来源：不再借用旧链路的 Can／Dem／NvM／Security，关闭 Dcm 来源身份不一致。
3. 删除帧／信号 host 链路（两个模板、“主机运行”页、`core/src/host/`、`render.rs`、`host_profile.rs`、`package_host_reference`）、单组件链路与外部 XSD／MOD 校验模式（设置项、`schema_zip`、全部 `*_legacy`）。`schema.rs` 的 XSD 校验仅保留为测试中的官方对照基准。删除前先把有独立价值的预期（协议、OS 时序、输入）迁到主线并通过。
4. 测试与开发工具回到正常入口（cargo test／unittest／vitest／node:test），与“用标准驱动方式替换桌面隔离验收设施”可并行。
5. 去除开发编号并按职责命名：产品代码、测试、fixture、工具、bin、目录、读者文档中不出现 Epic／Story 编号，也不用 “multi” 区分新旧实现；标准模块文件、头文件、内存段名称按 SWS BSW General 与 RTE 保持。
6. 生成管线结构与静态检查门槛：emitter 不 panic、不回读修补自己生成的 C，无法保证的前提返回 `PlanDiagnostic`；每个输出文件只有一个生成方；生成与集成模块 deny 级 panic／回读检查，其余模块固定基线逐步收紧。
7. 按所有权组织生成工程：静态 BSW、生成物、用户快照、适配层分目录，CMake 构建描述与 `ecu-tool` 来自同一清单。

**新基线达成条件：** `quality` 强制 Epic／Story 编号检查为零；旧链路代码已删，打开旧工程明确拒绝；必需 CI 覆盖主线全部不依赖官方档案的原生行为；交付包按所有权分目录且 CMake 与 `ecu-tool` 同清单构建通过；Linux、Windows 各至少一次 acceptance；ABI、第三方身份和资源摘要变化经审阅。

**之后：** 主线上逐模块标准整改（ECU 批次执行、CanIf、LSduR／PduR、COM、CanTp、Dcm、ComM／BswM、Det、OS／SchM、RTE／共享类型；Dem、NvM、Security 已随旧链路删除，不在本 Epic 整改，由 R7 重新实现）→ 主线交付与离线工具验证 → 开发反馈、CI 效率 → 严格生成 C 源码检查成为必需门禁 → 非实现者独立出口复验。已知遗留：Windows 并行 `E_OS_STATE`（若根因在共用 `runtime/os`，迁移时复现并归入 ECU 执行或 OS 整改）；CAN 整改遗留的 MISRA 人工评估与 c-check 清零由各模块承担。

Epic 9 出口前，R11 只允许需求与规范研究，消费者实施须等待出口。

### 2. R11：扩大 CAN 工程范围

29 位 ID、CAN FD、信号类型／布局、多通道及所需路由，闭合控制器—HOH—PDU—信号—应用关系，覆盖 2～4 路配置、通道隔离和真实布局组合。首个多项目消费者前固定基座／覆盖／变体与差异语义，随配置入口交付。放在诊断与网络管理之前；R11 的通信闭环不以 R7／R8 为前置。

### 3. R7：可配置 CAN 诊断与故障工程

DID／RID、服务／会话／访问、事件／DTC／监测源及持久策略，贯通 CanTp／PduR／Dcm、Dem／NvM。承接历史 Epic 2／Story 2.1 及旧 Epic 5 的诊断与持久部分。Dem、NvM 与安全访问在主线上重新实现，承接已关闭的 #47／#48／#49 及 #33 移交的 Dem 生命周期、NvM 持久独立预期。

R18 已定义的多块存储、默认值、CRC、冗余、版本／恢复及 Fee／介质软件模型随 R7 交付，覆盖批量 DID／DTC／NV 和故障注入；真实 Flash 取证不替代算法与软件恢复。多任务生成接续 [#198](https://github.com/g1331/autsaro/issues/198)，RTE 接续 [#212](https://github.com/g1331/autsaro/issues/212)，先于消费者验收；已定义的可选包也须有独立配置与行为证据。

### 4. R8：系统生命周期与 CAN 网络管理

EcuM／BswM 与 ComM／Nm／CanNm／CanSM 协调启动、通信组、请求／释放、NM、睡眠／唤醒及 NvM 关机协作，验证多网络映射、故障隔离与 bus-off 恢复。承接旧 Epic 5 的 NM 目标。R7 所需的有限启停与 R8 共用生命周期契约，应用服务接线复用 #212 并保持 #187／#195 的模块归属。

### 5. R9／R14：I/O、主控交互与 LIN

IoHwAb、所选 MCAL 的配置／软件接口与主机模型，SPI／IPC、PM 和 R14 已定义的 LIN 帧、角色、调度、设备消息及恢复在 MCU 前完成。定时器、ISR 上下文、控制器／收发器和存储软件行为先在主机验证，R10 只绑定具体外设、向量与引脚并测量硬件行为；不以“硬件相关”为由推迟通用软件。

### 6. R30：主机运行、仿真与可视化

从 #65 的生成 ECU 运行发展到场景驱动、虚拟总线／外设、存储故障、重放、网络／信号／诊断／任务／生命周期的运行视图，详见[发展顺序与接缝](host-simulation.md)。基础能力随模块接入，后续多 ECU、环境模型与指令级仿真按价值扩展，主机平台不依赖板卡就绪。

### 7. Epic 10：标准与主机工程交付验收

成果定义见 [#62](https://github.com/g1331/autsaro/issues/62)。

对[最低功能范围](reference-ecu.md)及至少两份集成配置累计复核，覆盖 R11、R7／R18、R8、R9／R14、OS／RTE、工程配置和必要健康子集，以及 R30 基础运行／仿真／视图。功能须分别有证据，不能因参考配置未启用就删去。完成标准、编辑／保存重开、生成、独立构建、主机行为／失败恢复与交接。软件差距回责任阶段修复；只有具体目标待验项带依据、责任和失败判据交给 R10。

### 8. R10：首个真实 MCU 接入与硬件取证

将主机已实现并验证的软件绑定到具体芯片／板卡，完成驱动／OS 端口、寄存器、向量、链接地址、引脚／对端及真实 Flash、唤醒、时序和资源取证，承接旧 Epic 6。实机集成等待 Epic 10，启动时间可以后移；通用配置、驱动逻辑、ISR 规则和软件恢复不能留到本阶段才补。中断与共享数据规则在前序开发时补入 [C 编码规范](../development/c-coding-standard.md)。

## 关键待决问题

1. **首个参考配置输入：** 采用哪份可合法使用的 R24-11 ECU Extract／BSW 描述／SWC 样例，哪些由产品提供、哪些由使用者提供；需要可追溯输入清单与正反例。
2. **诊断与 NM 剖面：** 按[参考工程要求](reference-ecu.md#首批场景与规模)固定 SID／子功能、DID／RID、会话／安全访问、物理／功能连接及独立正反预期，不能只用 `0x10`、`0x3E`、`0x22` 冒烟。NM 首批采用 ComM `FULL`＋主动 CanNm 与明确的常开组合，暂不引入部分网络或网关协调。
3. **容量与输入：** 参考样本覆盖批量 DID／DTC、多块 NV 和多任务；各阶段实施前核定具体数量、组合与预算，不能以缩小示例替代场景。事件—DTC 映射按所选 SWS／ECUC 明确，建议样本数不作为永久上限。
4. **真实目标与模拟器：** 板卡、MCAL 版次／许可、OS 端口、工具链和对端另行核定，不绑定主机交付日期。候选目标见[目标与交付](../architecture/targets-and-delivery.md)，模拟器按 [R30](host-simulation.md) 的用途、模型覆盖与依赖评估；可用于提前验证目标路径，也不替代主机平台或真实硬件取证。
5. **工作台内运行生成 ECU：** 接续 [#65](https://github.com/g1331/autsaro/issues/65)，Epic 9 后基于稳定 host-batch 契约在主线上重建，随 R11／R7／R8 接入并在 Epic 10 前完成隔离原生验收；重建前用 `ecu-tool verify` 和原生测试验证。
6. **稳定版本后的兼容策略：** 稳定版本发布前不兼容旧工程；稳定后策略另行决定（[#64](https://github.com/g1331/autsaro/issues/64)）。
7. **开源发布：** 许可、第三方权利、外部依赖和支持承诺在启动公开发布时单独核定；公开可读的规范与 XSD 不自动取得再分发权。

## 仍然有效的需求约束

### 版次与规范基线

- AUTOSAR：CP／FO R24-11 是唯一产品基线；规范 PDF 只存本机，引用文件名、条款号、版次和适用性判断，不复制原文。其他版次独立验证，不静默混版。资料入口见 [docs/official](../official/README.md)，规范核对方法见 [标准基线](../standards/README.md)。
- MISRA：C:2012 Third Edition＋AMD1–AMD4＋TC1–TC2，C99；适用项包含工具未覆盖的规则与指令。缺合法规范或工具证据时保持未核查并阻塞对应符合性结论。
- OS：完整参考 ECU 必须实际实现并验证所声明的 AUTOSAR OS 可扩展性等级；仅有原生 FreeRTOS 调度证据时只能称为有界 BSW-on-RTOS 剖面。

### 工程质量（原 QLT-1–QLT-6 要点）

- **标准与分析范围：** 盘点主线工程、runtime、生成来源与直接依赖，按 BSW、RTE、OS、生成配置、应用、主机适配和采用代码区分责任；核对模块 SWS、ECUC、通用 BSW 及条件适用的描述／MemMap 义务，不只查演示路径或新增函数。
- **结构与生成来源：** 一条生成主线、一种校验方式；按职责命名，不含开发计划编号；标准公开接口与主机适配分离；生成修复回到模板／emitter 来源并重新生成。稳定版本前旧 profile／旧格式工程与交付包按真实结构身份识别后明确拒绝，不静默误解析、不改写；用户的 R24-11 ARXML 源文件仍可导入新工程。契约变化同步配置、调用方、ABI、交付资源和 CHANGELOG，不能只更新资产摘要追认。
- **整改与偏离：** 目标是消除偏离；Mandatory 违反不得偏离；误报／不适用须有依据，采用代码不自动豁免。不允许规则降级、批量 suppression 或代理批准偏离；无法消除的真实偏离保持出口阻塞，由维护者另行决定。
- **测试与开发反馈：** 沿 npm、Cargo、uv 和已有测试入口分层；标准预期独立于被测实现，覆盖成功、边界、拒绝、恢复与已有行为；删除重复测试须证明没有丢失独立风险覆盖。
- **CI 效率与门禁：** 依据实际 job／step 耗时优化，复用锁定依赖缓存并按依赖并行；不减少平台、配置、样本或失败检查，不缓存扫描通过结果，不单纯延长超时。严格生成 C 源码检查进入每次 PR 的必需聚合检查和分支保护；违规、漏扫、工具失败、必需任务跳过／取消都不得合并。
- **实机前累计验收：** 见上文 Epic 10；未核查、失败或主机可完成但未做的项不能借“交给 R10”关闭。

### 参考 ECU 与各阶段验收要点

- **完整参考 ECU：** 至少两份有项目／变体差异的 R24-11 配置，覆盖[首批场景与规模](reference-ecu.md#首批场景与规模)，在声明主机目标上完成输入、生成、运行和交接，再选择具体板级组合复验。最小单网络、应用 DID 和故障示例保留为中间增量，不能代替完整出口；结论仅限实际验收组合。
- **R11：** 多种合法输入对应正确帧与应用数据，通道隔离和非法组合拒绝成立；主机 CAN FD 证据不外推到 MCU 或 CAN FD 诊断。
- **R7：** 至少两个不同故障可独立配置、往返与生成；分别触发、恢复、清除和同时触发有独立预期，一个故障不改变另一个；`0x19/0x01`、`0x19/0x02` 的数量、列表与状态掩码符合实际事件；逐故障跨进程保存、恢复和清除，存储损坏、写入失败或配置不匹配不伪装成空故障或成功；重复 DTC、非法监测引用、不支持子功能和超出声明容量明确拒绝。主机文件 NvM 不代替 Flash 证据。
- **R8：** 通信使用者请求和释放网络，ComM、Nm、CanNm、CanSM 与底层 CAN 的模式和回调形成闭环；对端可观察 NM PDU、网络运行、准备睡眠、睡眠与唤醒；错误模式、丢帧、bus-off 或唤醒失败有可观察状态和恢复／拒绝结果。不得用直接切换 Can 控制器状态（主机 `STARTED/BUS_OFF`）或周期报文代替 NM 证据。
- **R10：** 非实现者按交接清单在指定目标复现应用 CAN 信号、物理诊断、故障保存／重启／清除、网络请求／释放与睡眠／唤醒，以及适用的中断、时序、资源和异常恢复；目标证据与主机证据分开审查，不泛化到其他芯片。
- **交付完整性（跨阶段）：** 每个声明支持的组合列明产品通用 BSW、生成代码与描述、使用者应用、所选 RTOS 与合法目标驱动；另一位工程师不依赖仓库隐含文件或手补符号即可构建。生成源码占比不是验收指标。失败时保留可定位错误与既有输入／产物，不把旧构建或部分结果标为完成。
