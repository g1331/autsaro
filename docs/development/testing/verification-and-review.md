# 工程验证、调查与独立审查

本篇承接 [CONTRIBUTING](../../../CONTRIBUTING.zh-CN.md) 与[测试说明](README.md)，集中记录进入调查、工程推进基线、行为验证与证伪、代理独立审查及本地复核的具体要求。

## 进入调查与工程推进

- **同类基线对照**：以高质量完成项目为目标，按实际风险选择必要流程，不机械模仿举例的组织方式。每次交付以既有同类交付的工程习惯与质量为最低基线：开工时（写调查评论前）对照近期同类 Issue／PR 及实际代码，维度包括调查深度、代码习惯（命名、职责划分、复用已有入口、测试组织）、边界处理、测试和交接证据，交付前复核；精简只减少重复与无效工作，不削减必要调查、实现或验证，不等用户提醒后补齐。
- **进入调查**：进入条件未满足时先调查，把结论和确定的方案写回 Issue 评论再实现。调查评论写证据，不写执行计划：所选配置；按原文编号说明现有实现哪里成立、哪里有缺口；状态归属与真实调用闭包；方案理由及被否决的方案；ABI／交付契约影响；用哪些反例与变异证伪（范例：[#45 的进入调查](https://github.com/g1331/autsaro/issues/45#issuecomment-6192582796)）。新增校验、状态、标志或并发机制前，先追清已有校验链与实际调用闭包并写进调查；变异只做事后确认，不用来发现本应先查清的重复。
- **有证据的判断与核实**：给出有证据的专业判断，声称“已对照／已核对”时写明对象与维度，未覆盖的直接说明；受到质疑时核查依据并解释结论变化，不迎合反问，也不把日常技术选择交回用户。提请用户决定或确认前，先从 Issue／PR 记录、仓库与 CI 核实事项的当前状态：已解决的不再提出，例行跟进（如按规则新建 `known-gap` Issue）直接完成，确需用户决定的逐项在对话中提出并附推荐。
- **决定与授权**：普通方案、重构及有界风险按当前明确委托决定，不因历史待决重复索批。Issue 内 ABI／交付／第三方身份按规范决定并记入 PR／CHANGELOG。重大产品／公开合同、路线、发布、法律承诺、保护绕过及范围外操作仍按保留权限授权；提交至合并仅沿用当前授权，缺授权须说明。
- **持续推进与受阻处理**：按原始目标持续推进；阶段 PR 合并后继续剩余授权工作。先验证高风险机制。父项受阻则交付原验收内独立部分，注明承接者、下一动作及恢复条件；条件满足即验证与合并。重复失败沿用调查与补丁并修正根因。按风险和改动范围选择本地必需检查，完整矩阵由 master CI 验证。
- **举一反三与会话恢复**：用户指出一个例子时，先解决真实例子，再检查同一根因涉及的入口、调用方或同篇文档；不只改被点名的一处，也不据此扩展成无关的全仓治理。恢复或压缩会话后，从相关历史和当前仓库核对未完成目标，不用摘要中的“下一步”替代完整需求。
- **工具与脚本边界**：新建工程或子工程用生态认可的初始化工具；只有明确的长期团队用途才保留新增脚本，一次性探查不升级成仓库必经工具。验收工具受阻时优先评估已有安全替代入口，不让工具排障取代产品交付。

## 行为验证与证伪

- **正常入口实测**：行为改动从正常入口实际运行，按任务覆盖成功、失败和关键状态变化；构建、mock 或静态截图不能替代真实体验。区分浏览器、原生 Tauri／IPC、安装包和生成 ECU 的验证范围，未运行的层级不算通过。隔离条件不满足时，不退回用户桌面操作，也不为方便验收修改宿主全局设置。
- **证伪与变异要求**：测试要能证伪目标性质：拒绝测试只匹配共享错误码时，可能由另一项检查报告同一代码而通过，需同时断言对象位置；在 Issue 中声明某个边界“已有测试”前，先找到实际修改该输入的测试，并用放宽实现的变异确认它会失败。新增行为的每个可观察效果同样要有能杀死其变异的测试：删除某处写入或调用后全部测试仍通过、又找不到观察场景的，按死代码删除，不靠补 `Verifies:` 保留。
- **不掩盖失败**：不用放宽期限、弱化断言、重试、固定延时或扩大排除让检查通过；间歇失败先取得失败现场与输出，再按根因修复。子进程失败消息沿用已附带 stdout／stderr 的共用执行入口，不另写只报日志路径的错误。

## 代理独立审查

用户指定的审查模型、推理强度与服务配置必须原样使用，启动后核对实际配置；目录默认值不能代替读回，不可用时如实报告，不自行替换。配置只在会话中核对，GitHub 仅记审查 head、发现与处置，不写代理身份、模型、配置或会话信息。

模块整改、交付布局／ABI、并发或独占区等高风险改动须做一轮独立审查，可与 CI 并行。阶段提交不意味着逐段审查：作者完成相关范围的实现、自审和必要验证后，冻结完整改动与实际消费闭包，集中一轮独立审查；复用有效旧证据，核对累计影响与未覆盖部分。审查发现须注明位置与规范原文，实现者修复或说明不采纳理由，并对 finding 修改做定向复核；普通调整、措辞和哈希由作者自查。提前审查高风险基础机制须说明返工风险；平台取舍要求的逐处复核按其范围集中完成。

独立审查不带作者会话历史，默认只读复用现有工作树。开始时固定提交及已有修改，期间作者暂停源码修改；审查者不编辑、切分支或运行会改源码的检查。实验修改另行隔离。

## 本地复核与变异确认

- 修改 core 生成器或其模板时，交付前运行无测试目标过滤的 `cargo test --locked -p autosar-config-core`，同时执行 lib 单测与默认集成测试；`--test it` 和定向 native 结果只覆盖各自目标，Clippy 只编译检查。新增模板锚点时同步直接渲染该模板的单测，保留无残留锚点及缺失／重复锚点拒绝断言。
- 本地复核 Clippy 时按 CI 与 `verify` 的每条命令及其 feature 组合分别运行；`--workspace --all-features` 会打开 `native-webdriver` 等 feature，使 `cfg(not(feature = ..))` 分支不受检查，不能代替默认 feature 的检查。
- 按 feature 汇总多个测试二进制的结果时加 `--no-fail-fast`，否则 Cargo 在第一个失败的二进制后停止，后续套件既未运行也不报失败。
- 变异确认改动一方运行时源码时，无需更新资产摘要；每次构建从实际字节计算身份。以测试结果行和被测断言判断变异，不把编译失败当作杀死。第三方 source manifest 仍固定内核／端口身份，不能为变异自动更新。同一工作区先后构建两个变体时，旧二进制仍绑定旧来源身份；`runtime_contracts::` 检查当前资源目录会报告 `identity_differs`，变体应在各自检出中构建和运行。原生套件缺少 `AUTOSAR_CC` 等工具变量时以 `executable_environment` 失败，这不算杀死。
- OS suites 从 `autosar_tooling.config.ROOT`（可编辑安装所在检出）取运行时源码，在副本中变异时须让 `PYTHONPATH` 指向副本的 `tools/python/src`，否则测的仍是原检出；用 `-k NativeSuiteTests.test_<suite>` 选套件并确认实际运行了测试。
- 用短名选择 ARXML 容器做变异时同时匹配 `DEFINITION-REF`：`RxValue` 等短名在 CanIf、Com 等模块重复，选错对象会使拒绝测试因输入未变而失效。
- 生成器的模板编辑和测试变异按文本锚定运行时或生成 C 时，锚点不能依赖空白与换行：标识符用 `Edit::Token` 按完整 token 替换，`Edit::Every` 只要命中一处就不报错，会静默漏掉换行后的其余位置。
