# CP R24-11 与 AP R25-11：机器可读模型边界（研究笔记）

调查日期：2026-09-25。仅作 Wayfinder 后续架构决策的规范证据；不是 AP 实施承诺、互通/符合性结论，也不把 AP 当作当前 CP 开发的前置工程。以下“事实”来自指定版次官方文档/发布包；“推论/候选”是可验证的工程判断。`p.` 均指 PDF **物理页**（页脚 `n of …`），不是浏览器搜索摘录。先前的 `adaptive-feasibility.md` 仅用于定位文档，不作为下述事实的证据。

**同名/同类不等于同约束。** [AP R25-11 Manifest TPS §1.1.1，p.27–28](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_ManifestSpecification.pdf) 明说优先重用已有 `SwComponentType`、`CompositionSwComponentType` 等元类，同时增加平台专用扩展和约束；旧类的 CP 技术描述不能照字面移给 AP。[FO R25-11 ARXML Serialization Rules 变更记录，p.1](https://www.autosar.org/fileadmin/standards/R25-11/FO/AUTOSAR_FO_TPS_ARXMLSerializationRules.pdf) 标明 R24-11、R25-11 均无内容变化，这支持**本次**物理序列化规则可复用；并不抹平两个 XSD 或 TPS 语义的版次差异。

更正一个容易误读的命名：[AP R25-11 Manifest TPS §2.5，p.36](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_ManifestSpecification.pdf) 实际列 **五个** manifest 分区：Execution、Service Instance、Machine、Raw Data Stream、Software Distribution；本表只展开本任务要求的前三种，不宣称这三种穷尽 AP 输入。§2.2–2.4 p.34–35 还规定 manifest 的标准交换序列化为 ARXML，但机器实际上传格式由平台供应商选择且须保留原 ARXML 语义；设计 ARXML 不自动等于 manifest，引用的设计目标也不总须实际可解析。

## 可检验的最小共享接缝（**推论/候选**，不是通用 CP/AP kernel 建议）

1. **版本化 ARXML 文档层**：原始文件、root/schema hint、namespace、package/shortName、来源位置、跨文件引用/instanceRef 与分片合并，分别以 R24 `00053`、R25 `00054` 做 XSD 检查；保留原始版次和未解析状态。依据上表 FO 序列化/生产规则、AP §2.2–2.4 和 CP §14。XSD 只检语法结构，不能把 optional XSD 字段当作业务 optional。
2. **只共享“定义→值”导航的机制，不共享类型/规则**：能复用索引、ref target lookup、类型/多重性/约束诊断的基础设施；为 `EcucModuleDef`/`EcucModuleConfigurationValues` 与 `ApmcFunctionalClusterDef`/`ApmcFunctionalClusterValue` 分别做版次化适配。CP [ECUC TPS §2.3、§2.4，p.26、114–15](https://www.autosar.org/fileadmin/standards/R24-11/CP/AUTOSAR_CP_TPS_ECUConfiguration.pdf) 与 AP [Machine Configuration TPS §3.1–3.3，p.15–16、25–29](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_MachineConfiguration.pdf) 支持结构相似，但 AP §2.2 p.9 明说 **AP 不标准化 CP 式代码生成 symbolic names，AP variation/post-build variation 尚未厘清**；AP §2.1.2 p.9 又说 APMC 往往保留目标上的设计模型，而 CP ECUC 常追求独立完整的 BSW 配置。
3. **诊断报告设施可共用；语义校验器按版次、平台、模型阶段隔离**：FO [Serialization Rules §1，p.9–10](https://www.autosar.org/fileadmin/standards/R25-11/FO/AUTOSAR_FO_TPS_ARXMLSerializationRules.pdf) 与 AP [Machine Configuration TPS §1.1，p.6](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_MachineConfiguration.pdf) 指出约束有不同 imposition times。CP `IT_EcuExt` 平铺/拓扑规则、ECUC code-gen 条件，与 AP `IT_BefAraApiGen`、`IT_Mani`、`IT_CfgFc` 各有独立输入和时点；候选公共设施仅管理规范约束 ID、证据位置、严重性/阶段，不能跨平台直接调用校验函数。

## 尚不能从这些材料推断

- 未用真实 CP R24 项目工件与 AP R25 的设计/三类 manifest/APMC 成组跑解析、XSD、跨文件引用、约束阶段，因此**未知**最小公共数据结构是否比“ARXML 文档图 + 版次化适配”更深；FO [R25 序列化 §2.2.4，p.14–15](https://www.autosar.org/fileadmin/standards/R25-11/FO/AUTOSAR_FO_TPS_ARXMLSerializationRules.pdf) 的向后 schema 尝试不是跨版语义兼容证明。
- AP 的 `Process`、服务映射、Machine、APMC 以及 CP ECUC 在单一 XML namespace 中共存，不表示任一工具应接受所有类型组合；须按各自 TPS 的约束时点确定输入完整性。尤其 AP [Manifest TPS §1.1.2，p.28–29](https://www.autosar.org/fileadmin/standards/R25-11/AP/AUTOSAR_AP_TPS_ManifestSpecification.pdf) 说明 Diagnostic Extract 同时有 CP-only、共享、AP-only 部分，AP 诊断必须结合 CP Diagnostic Extract TPS 的共享章节；本笔记未完成那个 TPS 的逐条比对，不能声称诊断语义全面可复用。
- 没有硬件/指定 OS、工具链或平台供应商的目标配置样本，不能据 ARXML 结构声称生成物可在真实 AP 节点部署；目前可做的是主机侧静态解析/校验的候选边界实验，不应提前决定完整架构。
