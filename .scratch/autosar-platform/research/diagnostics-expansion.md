# CP R24-11：主机虚拟 ECU 的诊断闭环边界（决策输入）

**既定边界。** [首个受支持 CAN 档案](../issues/05-first-verified-profile.md#答案)已决定 CP/FO R24-11、先验证主机虚拟 ECU 的 CAN 信号通信，UDS/CanTp/Dcm 是紧接的增量；主机证据不等于真实 MCU、收发器或电气互通。下述是**可供选择的受支持配置子集**，不是声称完整 Dcm/UDS 已实现，也不是全模块部署于一个 ECU 或最终产品路线。

## 一条有意义的诊断闭环

- **可界定的无故障存储档案。** 一个生成的虚拟 ECU 与独立测试器在虚拟 CAN 总线上，针对已配置的物理请求/响应 CAN ID：测试器发 UDS `0x10`（默认会话与一个非默认会话）、`0x3E`（保持会话，含配置支持的抑制正响应形式）、`0x22`（至少一个来自运行中 ECU 状态而非固定回显的 DID）。选定一个只能在非默认会话读的 DID，另有一个足够长的 DID 响应以强制 FF/FC/CF 多帧发送；每个正/负响应、会话切换、超时回退都有可观察效果。Dcm 的会话切换须待响应发送确认，非默认会话有 S3 定时器，`0x3E` 支持 `0x00/0x80`，`0x22` 核查已配置 DID、当前会话和应用/BSW 数据源；所以仅注册 SID 或直接回显请求不能充当闭环。[Dcm §7.4.2.2，PDF 页111–112](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=111)、[§7.2.4.13，页71](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=71)、[§7.4.2.16，页207](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=207)、[§7.4.2.6，页135–140](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=135)。具体 DID 和允许的会话、长度、寻址/填充、时间参数须由该测试配置确定，不能由这份笔记冒充 OEM 定义。
- **必须打通的传输链（非所有功能都需启用）。** 测试器 ↔ 虚拟 CAN/已验证的 CAN Driver、CanIf ↔ **LSduR ↔ CanTp ↔ PduR ↔ Dcm** ↔ 所配置的应用/BSW 数据源，响应反向返回；还需已有调度/时钟及 Dcm 与 ComM 的通信状态交互。R24-11 的 CanTp **下层是 LSduR**，不可沿用早期“CanTp 直连 CanIf”的层图；LSduR 与 PduR 可在实现中合并，但各自路由语义/接口仍须满足。PduR 以配置的 I-PDU ID 做转发并承担 TP 的 StartOfReception/CopyRxData/CopyTxData/Indication/Confirmation，不解析服务 payload；既有 CAN **信号**路径不自动证明 TP 路径。[CanTp §1、§5.1.6–5.1.7，页9、19–20](../../../docs/official/R24-11/CP/Communication/AUTOSAR_CP_SWS_CANTransportLayer.pdf#page=9)、[LSduR §1，页7](../../../docs/official/R24-11/CP/Communication/AUTOSAR_CP_SWS_LSduRouter.pdf#page=7)、[PduR §1.3、§5，页16、24](../../../docs/official/R24-11/CP/Communication/AUTOSAR_CP_SWS_PDURouter.pdf#page=16)、[Dcm §5，页35–36](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=35)。此处“不启用 Dem/NvM”仅指以上三项服务的故障存储功能不在档案内；并非断言 Dcm 的全部可配置变体都不与它们交互。
- **主机行为证据。** 在真实调度的两个生成端点/独立测试器之间抓取 CAN 帧与端到端 UDS 结果：单帧请求→动态 DID 响应；长响应 FF→FC(CTS)→有正确序号/间隔的 CF→完成确认；非默认会话准许受限 DID、默认会话拒绝，`0x3E` 保持会话、停发后 S3 回默认；不支持 SID/DID、错误长度及超出配置缓冲给出符合启用子集的拒绝/失败；故障注入错误 CF 序号、丢 FC/CF 或溢出缓冲，应中止事务且不把部分数据交给 Dcm 当作完整请求。CanTp 对错误序号、N_Cr/N_Bs 超时、溢出及 Tx/Rx 完成确认分别有明确动作；Dcm 对失败接收不读半包，超大响应有 NRC `0x14` 路径。[CanTp §7.3.1–7.3.3，页29–35](../../../docs/official/R24-11/CP/Communication/AUTOSAR_CP_SWS_CANTransportLayer.pdf#page=29)、[Dcm §7.2.4.2.3、§7.2.4.8，页58、63–64](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=58)。这些是**可验收情景的推论**，不声称仅此就验证全部 ISO 一致性。

## Dem/NvM 是否同增量：两种不同承诺

| 选择 | 支持承诺与真实依赖 | 必须观察的额外证据 |
| --- | --- | --- |
| **仅会话/活数据诊断** | 对 `0x14`（清 DTC）、`0x19`（读 DTC）及 `0x85`（控制 DTC 设置）不宣称支持，且对未支持的服务/配置明确拒绝；该档案无故障记忆语义，因此**不需要为其虚构 Dem/NvM API**。可选有界 `0x2E` 写入运行态数据，但须有实际状态变化、长度/会话/权限检查，并不得暗称掉电保持。[Dcm §7.4.2.13，页181–183](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=181)。 | 会话与数据实际变化、负响应、双向多帧、错误恢复如上；重新启动后不承诺 DTC 或 RAM 写入内容仍存在。 |
| **同增量纳入 DTC 故障存储** | 若宣称 `0x19` 或 `0x14`，Dcm 按规范调用 Dem 的状态筛选/迭代/清除接口：Dem 必须有真实 monitor/event→DTC、UDS 状态位、事件内存、操作周期与清除/异步结果，不能提供固定零个 DTC 或假成功。至少界定子功能（如 `0x19/0x02` 按 status mask 和 `0x14` 配置组），不得一概宣称快照/扩展数据及 OBD。[Dcm §7.4.2.1、§7.4.2.4–5.2，PDF 页110–118](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=110)、[Dem §1，页22](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticEventManager.pdf#page=22)、[§7.11.2，页216–235](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticEventManager.pdf#page=216)。**Dem 可按配置仅用 RAM**；承诺跨复位持久化才要求 NvM、可持续存储后端、块读写与完整性/启停次序。Dem 明示 NvM 使用可关闭；NvM 的 NV block 经 MemIf/Fee 或 Ea。[Dem §7.11.5，页236–238](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticEventManager.pdf#page=236)、[NvM §5.2，页19](../../../docs/official/R24-11/CP/Memory/AUTOSAR_CP_SWS_NVRAMManager.pdf#page=19)、[§7.1.1–7.1.3，页25–29](../../../docs/official/R24-11/CP/Memory/AUTOSAR_CP_SWS_NVRAMManager.pdf#page=25)。 | 注入实际 monitor 失败/通过→状态掩码查询、DTC 列表变化→清除后消失；若仅 RAM，重启后如实表现为 RAM-only；若承诺持久化，等待 NvM 写完成、停止/重建**虚拟 ECU 进程**后读回，再清除并再次重建确认清除保持；注入块损坏/读失败验证有效性检查与初始化回退。Dem 启动要求 NvM 数据恢复先于 `Dem_Init`，关机 `Dem_Shutdown` 后写入且提前断电可能丢失最后周期事件。[Dem §7.1，页42](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticEventManager.pdf#page=42)、[§7.11.5，页236–238](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticEventManager.pdf#page=236)。这些场景为规范推导的验收建议，不是规范逐字规定的测试脚本。 |

**关键分界不是“诊断必须先实现所有 Dem/NvM”，而是宣称何种故障语义。** Dcm 的普通 UDS 支持表包含 `0x10/0x14/0x19/0x22/0x3E`，但这是**Dcm SWS 的范围**，不是任意局部产品配置已支持全部 SID；故障内存相关服务默认由 Dcm 经 Dem 实现，不能用直接编造响应绕过这个依赖。[Dcm §7.4.2、§7.4.2.1，页109–110](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=109)。Dem 的“永久事件内存”还是 OBD 的术语，不等同于任何配置的 NvM 掉电保持。[Dem §7.3.4，页50](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticEventManager.pdf#page=50)。

**其他边界及待决权衡。** `0x27` 需要 seed/key、失败计数与延时/安全级别等真实策略；`0x29` 进一步涉及证书与 Csm/KeyM，Dcm R24-11 仅覆盖所列 PKI 子功能；`0x34–0x38`/`0x3D` 牵涉实际存储、下载序列及引导加载器交互（Dcm 本身不打算用于 bootloader），不能在该虚拟会话/读数证据上顺带宣称编程/认证支持。[Dcm §4.1、§5，页32–36；§7.2.4.10，页64–67；§7.4.2.8、§7.4.2.19–23，页143、211–218](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=32)。CanTp 将未另行排除的 ISO 15765-2 建议直接委托给外部标准；Dcm 引 ISO 14229-1:2013/2020、ISO 14229-2:2021、ISO 15765-2/-3 并有选择性 2020 支持。官方 AUTOSAR PDF **不是这些 ISO 全文的替代物**：若要宣称 UDS/DoCAN 标准互操作，需合法获取、锁定适用外部版本并对照一致性验证；不能据上述有界实验推断全 ISO、OBD 法规或实机合规。[CanTp §3.1、§7，页15、23](../../../docs/official/R24-11/CP/Communication/AUTOSAR_CP_SWS_CANTransportLayer.pdf#page=15)、[Dcm §3.1、§4.1，页30–33](../../../docs/official/R24-11/CP/Diagnostics/AUTOSAR_CP_SWS_DiagnosticCommunicationManager.pdf#page=30)。本研究曾比较会话/活数据、RAM-only DTC 与 NvM 持久故障存储三种验收范围；后续已确定先做深包含 Dem/NvM 的 CAN 诊断档案，详见[阶段扩展路线](../issues/08-expansion-route.md)。这些是**产品验收范围选择**，而非固定规范先后顺序。
