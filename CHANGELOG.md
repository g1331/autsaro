# Changelog

[简体中文](CHANGELOG.zh-CN.md) · **English**

## Unreleased

- **Contract change:** CanIf follows the R24-11 CanIf contract. `CanIf.h` declares only standard services and callbacks: `CanIf_HostRxIndication` and its `Ecu_Status.h` include are removed, and the host Can driver reports receptions through `CanIf_RxIndication(const Can_HwType *, const PduInfoType *)` (SWS_CANIF_00006). With interrupt reception, `Can_Inject` now returns the driver's admission only; CanIf filtering and length checks are observed through Det and the upper-layer indication. The polling mainline behaves as before. `CanIf_Init` with an invalid set leaves CanIf uninitialized instead of keeping the previous set (SWS_CANIF_00661). `CanIf_Transmit` in `CANIF_TX_OFFLINE` returns `E_NOT_OK` without `CANIF_E_STOPPED`, which is reported only in `CANIF_OFFLINE` (SWS_CANIF_00382). A transmit confirmation suppressed by the PDU mode closes its request, so a later STOPPED no longer reports a sent frame as failed (SWS_CANIF_00739). Generated projects define the post-build set `CanIf_Config` in `src/CanIf_PBcfg.c` and declare it in `include/CanIf_Cfg.h` (SWS_BSW_00015); the BSW description adds CanIf's dependency on `Det_ReportRuntimeError`. Reviewed ABI impact: the only removed public symbol is `CanIf_HostRxIndication`, which no generated or application code calls; component contract headers and third-party identities are unchanged, so applications need no rebuild.
- **Breaking:** Mainline plans number CanIf Rx and Tx PDU handles consecutively from 0 per direction (SWS_Comtype_00007; `CANIF_HANDLE_SEQUENCE`) with at most 32 per direction (`CANIF_PDU_CAPACITY`). They require `CanIfRxPduCanIdType` `STANDARD_NO_FD_CAN` for the Classical-CAN-only controller (SWS_CANIF_00877). `CanIfDispatchCfg` must select UL `CDD` with the names `Ecu_HostBusSM_ControllerBusOff` and `Ecu_HostBusSM_ControllerModeIndication` (`CANIF_DISPATCH`, SWS_CANIF_00560/00692). The `standard-ecu` template now uses Rx handles {0, 1}, Tx handles {0, 1}, `STANDARD_NO_FD_CAN` and both dispatch names; existing projects must update these values before generation. `CanIfPrivateSoftwareFilterType` must be `LINEAR` and `CanIfPublicHandleTypeEnum` must be `UINT16`, matching the delivered filter and `Can_HwHandleType`; other values are refused with `TARGET_PARAMETER_UNSUPPORTED` instead of being ignored. A selected module that declares an `IMPLEMENTATION-CONFIG-VARIANT` other than `VARIANT-PRE-COMPILE` is refused at that module, because all configuration is generated before compilation.
- Add `python -m autosar_tooling requirements <document>`, which lists the official R24-11 requirement IDs of one specification (from `AUTOSAR_CP_MOD_SpecificationsARXML.zip`, now pinned in `core/resources/official.json` and downloaded by `fetch-official`) that no `Verifies:` comment in a test or disposition marker in `docs/standards.md` disposes of, with the counts per category, and the citations of IDs that R24-11 does not define (ADR 0017). `requirements --update <document>` commits the document's catalog (requirement IDs, life-cycle states and the archive SHA-256, no specification text) to `core/resources/requirements/`; the required checks then account every committed catalog without the archive (`requirements` with no document), and the `acceptance` workflow confirms that each catalog matches the archive.
- ECU delivery preview and generation for a project whose user application is not initialized now report `APPLICATION_UNINITIALIZED` at the composition and point to "Preview user application initialization…", instead of the misleading "multi-component configuration is not supported" diagnostic. Integration planning no longer carries the unreachable single-component branches; generated output is unchanged.
- Required checks verify the moved `standard-ecu` package with receiver Python 3.11, 3.12, 3.13 and 3.14 on Linux and Windows, replacing the `offline.yml` workflow that needed an unregistered self-hosted runner. The `bundles` workflow builds Linux and Windows installers on GitHub-hosted runners and uploads them per commit SHA; it no longer offers macOS.
- Add `python -m autosar_tooling fetch-official`, which downloads the official R24-11 XSD, ECUC MOD and modeling showcase archives to the locations in `core/resources/official.json` and verifies their pinned SHA-256; the showcase archive now has a pinned digest. The `official` comparison suite runs on GitHub-hosted Linux and Windows runners (manually, daily, and for pull requests that touch definitions, rules or the official tests) instead of an unregistered self-hosted runner; it is not a required check.
- Make reader-facing root documents English by default, retaining complete Chinese versions with the `.zh-CN.md` suffix and updating reciprocal language links.
- License original project code and documentation under Apache-2.0; add package metadata and LICENSE/NOTICE files to delivered projects. Third-party content retains its original licenses.
- Use npm, Cargo, and uv directly for development, removing duplicate task orchestration and separating tooling source, tests, and optional skill maintenance.
- Support Python 3.12+ for development and 3.11+ for offline tools without requiring a specific patch version; use Vitest for frontend tests.
- Separate project, editing, delivery, and settings logic while preserving IPC and atomic-commit boundaries. Draft changes invalidate previous batch previews.
- Assign new trusted identities when resource paths or tools change. Existing sealed packages must still match their original producer and are not rewritten in place.
- Separate basic tests, official comparisons, and native execution tests; add frontend behavioral regression coverage.
- Add a contributor guide, basic CI, dedicated acceptance entrypoints, and asset-maintenance documentation.
- Complete Git line-ending rules needed to preserve runtime byte identity.
- Plan projects with a single application component on the multi-component mainline; a composition with only service components is rejected with `APPLICATION_COMPONENT_MISSING`.
- Mainline Dcm refuses ReadDataByIdentifier requests with more DIDs than the configured `DcmDspMaxDidToRead` with NRC 0x13 (SWS_Dcm_01335). `Dcm_ConfigType` gains `max_did_to_read` (0 when not configured) and plan descriptions record `maxDidToRead`.
- Mainline CanTp reports `CANTP_E_RX_COM`/`CANTP_E_TX_COM` runtime errors on timeouts (SWS_CanTp_00229). The generated host target receives them through a Det runtime callout and reports them as HostBatch transport failures.
- Mainline projects with one application component, one 32-bit CAN receive and transmit signal and an application DID deliver `verification/inputs.json`, so `ecu-tool verify` checks the reference echo behaviour.
- Mainline plans reject CanIf PDU handles above 255 with `CANIF_HANDLE_WIDTH` (the delivered `PduIdType` is `uint8_t`) instead of `CAN_ID_CONFLICT`, and report a missing selected BSW entry at the module reference that names it instead of an unrelated object.
- Mainline planning rejects runnable symbols that shadow the generated OS counter service producers (`OsService_<Counter>_*`, `Rte_Call_OsService_*`) with `SYMBOL_PRODUCER_DUPLICATE`.
- **Breaking:** The ECU generation mainline profile is now named `singlecore-ecu-v1` (previously `singlecore-multi-swc-v1`), and every project validated with built-in rules is planned on it, including projects with one application component.
- **Breaking:** The built-in `standard-ecu` template (previously `standard-ecu-v1`) creates a single application component project on the mainline with ComM/BswM mode management; its create-only application seed is the reference echo application that `ecu-tool verify` checks.
- **Breaking:** Workbench projects and native deliveries recorded for `epic4-win64-sr-cs-v1` or `singlecore-multi-swc-v1` are refused on open without changing files; the desktop no longer imports `autosar-ecu-handoff-v1`. Their ARXML sources can be imported into a new project.
- **Breaking:** Remove the frame/signal host chain (templates `can-empty-v1` and `can-signals-v1`, frame/signal and diagnostic/DTC editing, host source delivery and builds, and the dual-ECU and diagnostic runs of the host run page), the single-component chain, and the external XSD/MOD validation mode. Projects recorded for `host-can-v1`, deliveries whose `target.json` names `profile: "host"`, and `autosar-host-handoff-v1` handoffs are refused on open without changing files; their ARXML sources can be imported into a new project. New projects use the mainline `standard-ecu` template. The workbench cannot yet run a generated ECU interactively (#65); host behavior is verified with the packaged `ecu-tool verify`, the workbench's fixed host verification, and native tests.
- Retired `xsdArchive`/`modArchive` entries in the settings file no longer prevent startup: the workbench ignores them, shows a notice in Settings, and drops them on the next settings save. The workbench no longer reads `AUTOSAR_XSD_ARCHIVE`/`AUTOSAR_MOD_ARCHIVE`; official archives are used only by development-time `official-oracles` comparison tests.
- **Contract change:** The component contract kit ships the mainline `Platform_Types.h` and `Std_Types.h`, and `Rte_Type.h` only includes `Std_Types.h`. Previously `Rte_Type.h` defined `uint8`/`uint32` itself over a legacy `Std_Types.h` in which `boolean` was a `uint8_t`; the mainline `Platform_Types.h` defines `boolean` as `_Bool`. Applications compiled against the old contract must be rebuilt against the new kit.
- `Ecu_Target.h` drops the `Ecu_TargetInitializeRte` declaration that only served the removed chain, and `Ecu_TargetReportTransportTimeout` is no longer guarded by `ECU_MULTI_COMPONENT` (unchanged signature). `Ecu_Target.c`, `Ecu_HostBridge.c`, `SchM_Diagnostic_Host.c`, and the `Ecu_Config.c.in` template drop branches the mainline never compiled. Their asset digests change; apart from that removed declaration, mainline preprocessed sources and the generated `src/Ecu_Config.c` are unchanged, and no third-party source is involved.
- Remove runtime assets that only served the removed chains (`runtime/src`, `runtime/include`, `runtime/host`, reference package notes and vectors, `bsw-v1.json`, and others); the 13 mainline BSW sources are now listed directly in `assets-v1.json` with unchanged bytes. Mainline deliveries no longer contain files no program compiled or used: `src/Ecu_Diagnostic.h`, `tools/ecu/templates/Application.c.in` and `Rte.c.in`, the duplicate `tools/multi/include` headers, and `inventory/contracts/bsw-v1.json`; the delivered `include/Rte_Type.h` no longer includes `<stdint.h>` directly. The packaged `ecu-tool build` no longer accepts `--mode host` and `ecu-tool verify` no longer accepts `--report-path`. Remove the `bsw-catalog` and `input-oracles` development commands and the `--builtin-only` option of the desktop acceptance (the built-in scenario is now the only one); C static analysis now uses the three mainline samples.
- The integration panel's CAN ID and application period editor also works on mainline projects; when the Com Tx main function shares the application trigger, its timebase and the transmit PDU periods follow the application period.
- Mainline BSW sources now come only from the mainline runtime directory: the host CAN driver (Can, Can_Host, Can_HostLock) and Ecu_Status moved there with unchanged bytes, so their asset digests are unchanged and only the recorded paths change. No public signature, layout, handle or wire format changes. Mainline deliveries no longer contain five headers that no program compiled (`include/Can.h` legacy aggregate view, `Dem.h`, `NvM.h`, `Security.h`, `Ecu_DcmCallbackTypes.h`); compiled sources and headers are byte-identical.
- Mainline producer metadata matches the delivered bytes: the DID read service is consumed by the mainline Dcm, the CanTp/Dcm scheduler headers and OS counter services name their actual declaring files, and `integration.json` `originalBswSources` lists only files delivered unchanged (generator-extended templates are generated outputs).
- HostBatch no longer waits out a host timer period for each output frame before confirming it. The target wakes the waiting control thread through the new `Os_TargetNotifyNative`, and `Os_TargetWaitTick` returns `E_OS_NOFUNC` early on that wake. On Windows, a timed 1 ms wait lasts about 15.6 ms, so a 1000 ms batch with periodic output could exceed the 5000 ms HostBatch watchdog under load (#61). Deadlines and automotive time are unchanged.
- Generated host ECUs confirm a frame sent before an epoch's cycle only after that cycle, whenever the host thread reports it, so CanTp timers started by a transmit confirmation (such as N_Cr after a flow control) no longer expire one cycle early depending on host scheduling, and the packaged `ecu-tool verify` no longer fails intermittently on its N_Cr check (#86).
- Remove the `probe`, `os`, `os-arti-native`, `os-counter-service` and `protocol-oracles` development commands; the CLI keeps `doctor`, `verify`, `quality`, `c-check`, `assets` and `desktop`. The native OS suites run with `unittest` (`tests/python/native/test_os_suites.py`, filterable with `-k`), the protocol oracles in `cargo test --test it -- protocol_oracles::`, and the managed-process probe is the test helper `tests/python/process/probe.py`. Core integration tests are grouped into the `it`, `native` (`native-tests`) and `official` (`official-oracles`) binaries by capability; required CI now runs every native suite and the OS suites on Windows and Linux, and C static analysis adds a `no-diagnostic` multi-component sample. The delivered `runtime/os/README.md` shows the new OS suite commands.
- On Linux and macOS, managed execution waits for the process supervisor's authenticated readiness reply instead of the appearance of its socket file, so a command started right after the supervisor no longer fails intermittently with `Connection refused`.
- **Breaking:** Native deliveries use the handoff format `autosar-workbench-handoff-v3`; the desktop refuses `autosar-workbench-handoff-v2` packages on open without changing files, and their ARXML sources can be imported into a new project. Inside a package, the seal guard is `tools/sealed_package.py` with `tools/build-tool-inventory.json` (format v2), the copied standalone tool is `tools/standalone-ecu-tool.py`, the asset inventory is `inventory/contracts/assets.json` (format v2, one `ecu` profile), `workbench-ownership.json` has `formatVersion` 2 with producer IDs `autosar-workbench-config` and `autosar-workbench-build`, `integration.json` is `autosar-ecu-integration-v2` and `contract.json` is `autosar-component-contract-v2`. Plan descriptions (`formatVersion` 2) and `integration.json` name the component composition `composition` (previously `multi`). The generated ECU stack hooks are named `Ecu_Stack*`, and `Ecu_ProfileConfig.h` no longer defines the unused `ECU_MULTI_COMPONENT`. BSW public interfaces, the component contract headers and third-party identities are unchanged; applications need no rebuild.
- The repository root is a Cargo workspace with one `Cargo.lock` and one `target/`; select a crate with `-p autosar-config-core` or `-p autosar-config-desktop`. The mainline BSW runtime moved from `runtime/multi` to `runtime/bsw` with unchanged delivered paths and bytes. Integration modules, test fixtures, the C analysis sample `component-pipeline` and the desktop scenario `composition-editing` are named by responsibility, and `quality` rejects development plan numbers in repository paths and text.
- Every generated ECU file has exactly one producer. Generation rejects a second producer of a path (`OUTPUT_PRODUCER_CONFLICT`), a runtime template left unrendered (`OUTPUT_MISSING`) and a template that no longer contains its edit anchor (`TEMPLATE_ANCHOR`) instead of overwriting or patching generated text. Generated sources and README are byte-identical. The unused `runtime/ecu/include/Rte_MemMap.h` asset, which the generated `include/Rte_MemMap.h` always replaced, is removed from the asset inventory, so the delivered `inventory/contracts/assets.json` and the rule-set identity change.
- Generation reports a premise that the validated plan does not guarantee (a missing owner, mapping, referenced object or ECU plan part, or a zero period) as a diagnostic at the source object (`PLAN_PREMISE`, `REFERENCE_UNRESOLVED`, `INPUT_OBJECTS_MISSING`, `ECU_SOURCE_CLOSURE`) instead of panicking. Clippy checks both crates with its default lints as errors; the generation and integration modules also deny `unwrap`, `expect`, `panic!` and patching of rendered text.
- The built-in SWC template vocabulary no longer offers `ALIVE-TIMEOUT`, `HANDLE-NEVER-RECEIVED` or `HANDLE-TIMEOUT-TYPE` under a `P-PORT-PROTOTYPE`; R24-11 allows them only in receiver com specs. The `official` suite compares built-in ECUC definitions with the ECUC MOD and the template vocabulary with the R24-11 XSD (#72).
- **Breaking:** Generated ECU projects are laid out by ownership (ADR 0016): static BSW in `bsw/{include,src}`, host adapters and both mains in `integration/{include,src}`, the OS adaptation in `os/`, the fixed kernel in `kernel/` (`StackMacros.h` in `kernel/compat/include`), every configuration-derived file in `generated/{include,src,descriptions}`, component skeletons in `generated/templates` (not compiled), sealed application snapshots in `app/<component>/<component>.c`, configuration snapshots in `inputs/`, and the ledger, handoff, `integration.json`, `contract.json`, timing and verification inputs, asset inventory and seal (`files.list`, `files.sha256`) in `meta/`. Regeneration changes only `inputs/`, `generated/`, `app/`, `meta/` and the root `README.md`, `target.json` and `CMakeLists.txt`; the packaged `tools/ecu-tool.py` no longer embeds configuration-dependent expectations, which move to `meta/seal-policy.json`. Every runtime `*_MemMap.h` and the `SchM_*`, `Rte_*_Type.h`, `Os_Cfg.h`, `Os_Arti.c` and `Ecu_Config.c` templates are generated outputs (SWS_MemMap_00032, SWS_Rte_07501), so the Can main functions are recorded as declared by the generated `SchM_Can.h`. The handoff format is `autosar-workbench-handoff-v4`, the ledger has `formatVersion` 3 and `target.json` is `autosar-build-target-v2` with an `entries` map of the HostBatch and probe mains; include paths no longer contain the project root, and header names must be unique across them ignoring case (`backend.prepared.include_name_conflict`, SWS_BSW_00171). The desktop refuses `autosar-workbench-handoff-v3` packages, and generation, preview and the packaged tools refuse a package with a top-level `files.list`, without changing files; their ARXML sources can be imported into a new project. The component contract package keeps its headers in place and moves its seal to `meta/`. Review: generated and delivered C and header bytes are unchanged and every program compiles the same translation units, so the BSW public interfaces, component contract headers and applications need no change; FreeRTOS bytes are unchanged and only the path of the project's own `StackMacros.h` compatibility header moves.
- Generated ECU projects contain a `CMakeLists.txt` built from the same sources, flags, include paths, kernel patches and libraries as `target.json`, for IDEs and CI (`cmake -S . -B <build> -G Ninja`). It refuses a build directory inside the package, patches a copy of the kernel in the build directory and leaves the sealed files unchanged; it does not check the pinned toolchain identity or run `verify`, which stays with `tools/ecu-tool.py`. Required CI builds a sample with CMake and Ninja and compares its translation units, sections and output with the `ecu-tool` build; development installs CMake 4.4.4 and Ninja 1.13.2 through the uv `build` group, which is not delivered.
- **Contract change:** HostBatch execution and its receipt are declared in a new delivered header, `Ecu_HostBridge.h` (`Ecu_HostSink`, `Ecu_HostBatchExecute`, `ECU_BATCH_WATCHDOG_MS`). These declarations move out of `Ecu_Target.h` and `Ecu_HostBatch.h`, which keep the target owner and the codec respectively. `Ecu_HostBatchExecute` now returns `E_OK` whenever the batch ran and its receipt (`COMMIT_OK` or `COMMIT_ERROR`) went to the sink, and returns a refusal status only when nothing ran, after discarding the staged inputs itself. Previously `E_OS_VALUE` meant either outcome, and the HostBatch main had to inspect and reset the staging. `Ecu_Target.h` drops `Ecu_ApplicationState`/`Ecu_ApplicationInspect` (declared but never defined) and `Ecu_TargetRecordReceive`/`Ecu_TargetReceiveStatus`, and the generated `Ecu_TargetConfig.h` drops `ECU_TARGET_RX_CAN_ID`/`ECU_TARGET_RX_DEADLINE_MS`; the mainline had no callers, because COM deadline monitoring owns reception timeouts. The HostBatchV1 line protocol and the BSW public interfaces are unchanged. Review: these are project host-adapter interfaces, not AUTOSAR interfaces; only the delivered `integration/` sources, the generated `Ecu_TargetConfig.h` and `Ecu_RuntimeConfig.c`, and their asset digests change. No third-party source is involved, and applications need no rebuild (#39).
- Generated ECU startup runs in up to eight BSW initialization stages (stage 7, CanTp and Dcm, exists only with a diagnostic transport). A test build (`ECU_TARGET_TESTS`) can fail any stage through `Ecu_TargetTestFailStage`. The ECU then closes with `ShutdownOS(E_OS_STATE)` before producing any output, and `Ecu_StackRetire` undoes only the stages that began, newest first, reporting each through `Ecu_TargetTestRetire`. Previously the mainline had no startup failure seam, and retirement deinitialized every module. The private `Ecu_StackBootstrap`/`Ecu_StackRetire` hooks take the reached stage. Production builds do not link the test hooks (#76).
