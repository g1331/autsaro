# Autosar Classic 产品简述

本产品面向集成 AUTOSAR Classic ECU 的使用者，交付自有 Classic 基础软件栈，以及配置、校验和代码生成工作台。完整参考 ECU 沿已确定的固定 FreeRTOS 内核＋自有 AUTOSAR OS 语义＋有限单核策略扩展路线，逐配置、逐目标验证；不重新打开 Epic 4 的 OS 选型。通信、诊断及后续模块的 BSW 实现由本产品提供，不依赖另一套现成协议栈。使用者从新建配置或导入多文件 ARXML，到安全编辑、校验和生成可交接工程；构建及虚拟 ECU 是可选验证能力，不是使用 Configurator 的前提。已有 Windows、Linux 受控主机目标与独立交接能力是扩展起点；指定 MCU 另行验证。长期方向是逐阶段覆盖所选 Classic 版次中当前有效的运行模块与多个目标平台，不表示一个 ECU 同时启用全部模块，也不预设工作量或发布日期。

主要使用者是 ECU 集成工程师和 BSW 开发者：他们需要把系统/ECU 配置、应用接口和目标环境接成可交付工程。产品维护通用 BSW 实现，按项目生成配置与必要接口/集成代码，并提供完整输入、产物、构建和行为证据；不以“生成源码占比”衡量质量，也不替使用者生成车辆功能算法。Vector MICROSAR Classic＋DaVinci Configurator、EB tresos AutoCore＋Studio 是产品形态的参照，不是当前功能或符合性声明。

## 完整产品的功能构成

1. **输入与建模：**接受所声明范围内的系统/ECU 描述、ECU Extract、BSW 模块描述与配置，以及应用 SWC 描述；支持新建、导入、引用/变体校验、安全编辑与可追溯的往返。当前主机子集远未覆盖这些输入类别，不能把一般 ARXML 导入能力等同于完整 ECU 工程输入。
2. **配置与生成工具：**呈现模块和跨模块依赖，校验参数及目标约束，生成实际需要的 BSW 配置、RTE/应用接口和目标集成文件；明确哪些产物是复用的栈源码、哪些按 ECU 生成，附构建与交接清单。
3. **可运行软件栈：**维护声明支持的通信（包括适用的网络管理）、诊断、系统、存储、I/O、安全等 Classic BSW 模块实现及其真实接口行为；以选定 OS/RTOS 与具体目标驱动形成可运行闭包。通用应用算法、芯片厂商专有驱动和未获权利的软件不默认为本产品自有实现。
4. **集成与证据：**支持独立构建、Windows 虚拟 ECU 验证和指定硬件目标验证，并对配置、目标、工具链、版本和适用规范义务出具可复现的成功、拒绝、恢复与未验证记录。

“完整产品”意味着上述链路能对声明支持的典型 ECU 工程从合法输入走到交付与复验，并持续扩大所选版次的适用模块与目标覆盖；它不是仅有配置编辑器、单条主机协议链，也不等于所有车辆应用、芯片驱动、版次和安全认证一次到位。各模块的完整支持配置及规范义务须经独立盘点和实证定义，当前尚无可据以宣布整体完成的单一百分比分母。

**已确认的第一条产品链：通用 CAN＋诊断参考 ECU。**它不承担某一车型或 T-Box 的专属业务：使用者给出受支持的 ECU/BSW 配置和一个示例 SWC 的接口描述，配置 CAN 信号收发与物理诊断连接，获得含自有 BSW、必要生成物、应用接口及目标依赖清单的独立工程；先在 Windows 虚拟目标、再在指定 MCU 上复现通信、诊断和故障恢复。示例应用只用于证明接口闭合，不构成车辆功能算法产品。Epic 4 的输入剖面、应用 DID 和 OS 主路线已由最终架构及集成契约固定；完整诊断/NM 子集和首块 MCU 板卡仍在后续 Epic 决定。

网络管理属于这条 CAN 参考 ECU 产品链的完整交付范围，须明确区分 ComM 的通信模式请求、Nm 通用接口、CanNm 总线专属状态机及 CanSM 控制器/总线状态管理。开发过程中可用“常开 CAN、无网络管理”的受限配置先验证通信与诊断，但不能以它作为首个完整参考 ECU 的退出结果。首个完整参考 ECU 应在声明的单 CAN 网络配置下验证请求/释放网络、NM PDU、睡眠/唤醒及异常恢复；主机 `STARTED/BUS_OFF` 切换或周期报文不能充当这些证据。部分网络、网关协调与其他总线 NM 留到相应配置和对端可验证时决定。

使用者应能从配置或真实 ARXML 输入，看到保存及生成差异，得到完整工程，离线构建、运行、复现成功与拒绝场景。无法安全保留的引用、影响生成的未知配置和未支持变体须明确拒绝。主机行为、内部已审支持、实机支持与公开发布是不同声明。

“完整”有两层验收口径：近期对每个声明支持的 ECU 配置，交付它运行所需的代码、配置、接口、目标适配和可复现行为闭环；长期逐步扩大所选 Classic 版次中当前有效运行模块的覆盖范围。当前已有 CAN 主机信号链和有界 DoCAN 行为；旧目标`Os_Advance`是虚拟时间调度器；Epic4新目标已把声明的BSW／应用路径接入固定FreeRTOS backend，并完成独立主机复验。已有实现与任务完成记录是起点，不能由历史任务数量推算 Classic 总完成率，也不能把单项 story 完成等同于产品阶段退出。以后每个受支持组合分别记录版次、配置、RTOS 及其适配、目标、工具链、规范义务和验收证据。

维护者已确认 Epic 4 主路线为 FreeRTOS 固定内核＋自有 AUTOSAR OS 语义实现＋有限单核策略扩展，目标单核 SC1，保持原生 Windows。复用内核降低全新 CPU 机制开发风险，产品承担汽车语义、策略扩展和长期维护；Trampoline/ATK2 等保留参考和备选。路线决定不等于生产依赖已集成或等级能力已通过：必须对所声明的 R24-11 配置、接口与运行义务逐项取证，不能把原生 FreeRTOS 或 Os_Advance 称为完整 AUTOSAR OS。具体交付版本、许可/补丁、端口和 MCU 证据按目标固定。Epic4的22条故事已完成BMad验证和独立主机交接；后续Epic仍未启动。

统一 Configurator 工作区和应用集成须共同细化用户旅程、对象关系与责任边界，再据 R24-11 方法学及 SWS 核定输入、生成和运行契约，沿 Epic 4 已定 FreeRTOS 与汽车 OS 语义路线扩展，不重新选型。2026-10-03 用户暂定界面／透明珊瑚 A 身份并授权 R5 规划，随后确认正常校验规则由软件实现，不让用户准备官方 XSD／MOD。正式 Epic 7 的 11 条故事按此契约修订，实施就绪以[最新检查](implementation-readiness.md#2026-10-03-r5--epic-7-实施就绪)为准，全部 backlog，不表示功能已实现。首个 MCU 的板卡、工具链、合法驱动及真实对端仍在对应目标规划中决定。

## 产品方向与阶段原则

- **当前基线：**Epic 1、3、4、7、8 保留其原定范围的完成记录；后续工程治理已形成 Windows／Linux 受控目标及无 checkout 的原生分发与交接起点。新增 Epic 9／10 仍为 backlog。主机成果不继承实机、硬实时或认证声明，macOS 原生能力仍未验证。
- **工程工具优先：**先让真实 ECU 工程在统一工作区中创建、导入、编辑、保存、校验和生成，再扩大应用集成与可配置 CAN 诊断。软件独立实现并随包提供声明支持的结构、模块参数、引用与跨模块规则及自有模块定义；官方 XSD／MOD 是研发参考，不是用户运行时前置条件。第三方定义为可选扩展，编译与虚拟运行另需实际执行工具。
- **首个完整 CAN 工程与 MCU：**沿诊断、生命周期／网络管理、存储及必要 I/O 闭合主机工程，再在具体板卡、工具链和合法驱动条件下独立复验。目标可行性调查可以提前；购买、绑定目标和宣布支持需要相应依据。
- **扩展阶段：**提前规划 CAN 29 位、FD 与多通道；随后按真实依赖和对端扩大网络、横向服务与专业工程。顺序是产品路线，不是所有模块串行等待前一项结束的约束；可复用基础和独立目标调查按依赖推进。
- 完整参考 ECU 必须实际实现并验证其声明的 AUTOSAR OS 范围；若仅有 FreeRTOS 原生运行证据，只能声明有界的 Classic BSW 在该 RTOS 上运行，不能声明完整 Classic 平台。主机虚拟运行、指定芯片实机运行、第三方互操作、完整标准义务、功能安全和公开发布是不同的声明。Windows 运行可形成有边界的主机交付，但其调度和时间证据不能外推到硬件；取得板卡、合法工具及目标证据后，才验证具体芯片和工具链的实际行为。其他规范版次独立验证，不静默混版或迁移。
- Adaptive Platform 是单独的产品与部署方向。待多类 Classic 能力稳定、选定 AP 版次及真实模型和运行样本后再决定是否立项；不预造共用 CP/AP 模型或运行实现。
- 当前只在本地研发。开源是长期方向，发布许可、第三方权利、外部依赖和支持承诺在启动公开发布时单独核定；公开可读的规范和 XSD 不自动取得再分发权。

## 长期候选路线

本节是长期方向的唯一候选目录；PRD 细化已确认需求，epics 承载正式实施定义，sprint 承载实施状态。`R5–R29` 对应本次讨论中的候选 Epic 5–29，**不是正式 Epic 编号**，不复用既有 Epic 5、6 的历史身份，不直接生成 sprint 条目。候选正式化时分配未使用的 Epic ID，保留本节来源引用；拆分、合并、顺序调整均保留需求去向。每项的目标是可用工程成果，不是一次完成同名模块族的所有配置。

2026-10-03：候选 **R5 已正式化为 Epic 7**，来源范围与完整退出保持本目录定义，细节见 [PRD](prd.md#r5-选定范围与完成契约)、[Epic 7](epics.md#epic-7-可独立使用的统一-ecu-工程配置工作台)和[就绪结论](implementation-readiness.md#2026-10-03-r5--epic-7-实施就绪)。2026-10-10，R6 首批配置按正式 Epic 8 完成；未选扩展及 R7–R29 保持候选，不按相同数字登记 sprint，旧 Epic 5／6 的追溯身份不变。

**近期推进顺序：R5（正式 Epic 7，done）→ R6 首批（正式 Epic 8，done）→ Epic 9：运行时、生成 C 与开发工程体系整顿 → R11 → R7 → R8 → R9 → Epic 10：标准与工程交付验收 → R10。**R11 继续在诊断和网络管理前建立 29 位 ID、CAN FD、信号类型／布局、多通道及所需路由的基础；2026-10-10 授权在其前先整改现有交付基线，并在实机前复核累计成果。Epic 9／10 是正式成果编号，不等于候选 R9／R10；全部既有编号、已完成范围及历史证据保留。

R7 贯通 CanTp／PduR／Dcm、Dem／NvM，逐服务验证读写、例程、权限、超时及真实状态变化。R9 的 CDD 按具体场景提供，不造万能空壳。R7 所需有限启停与 R8 共用生命周期契约；R9 在所需应用／调度基础成立后可独立推进，R10 的目标调查不必等待整个阶段顺序结束。R11 的通信工程闭环不以尚未实施的 R7／R8 为前置；其表中诊断／NM 复用按后续所选组合接入。R6 与 R11 规划时共同核对通道、信号类型与应用映射契约；主机 CAN FD 证据不外推到 MCU 或 CAN FD 诊断。

### 与候选目录并行的产品扩展轴

- **新增 MCU／工具链：**每个目标单独固定驱动、许可、端口、资源与实际行为，不用一个无限扩张的 Epic 承担全部平台。
- **规范版次／迁移／外部互操作：**按实际版次及输入／对端形成增量，显式迁移，不继承 R24-11 证据。
- **开源发布：**每次公开发布单独核定许可、依赖、升级与支持承诺；本次本地规划不授权 push、发布或远端操作。
- Adaptive Platform 独立立项；学习层继续保持下文的后期边界。

### 滚动规划与近期边界

R5 配置工作台已有交付基础；2026-10-10，R6 首批多组件配置已按正式 Epic 8 完成模型、通信／调度、源码保护、工作台编辑与独立交接，并经 PR #15／#16 的必要 CI 和合并交付。支持范围与未验证边界见[现有规格](../specs/spec-multi-component-scheduling/SPEC.md)及[验收结果](../specs/spec-multi-component-scheduling/acceptance.md#2026-10-10-首批配置验收结果)；候选 R6 来源及未选的队列、模式、异步和多实例扩展保留。R7 的历史需求继续保全，不因尚未准备开发而丢失。其他候选保持成果级定义，依真实约束调整，未决定的接口、容量、参数和目标不得编造成可执行 Story。每个成果需贯通可编辑输入、校验、生成与工程交接；实现方用独立构建和行为验证所声明能力，用户的配置／生成主流程不依赖这些可选工具已安装。

进入实施前，用 PRD、UX、架构与 Epic／Story 补齐选定范围，经过 BMad 就绪检查，再更新 sprint。历史 R5／Epic 7 规划检查为 PASS，11 条故事曾初始 backlog；当前任务状态以 sprint 为准。`backlog` 不等于 `ready-for-dev`，进入每故事前仍要形成开发规格、冻结起始提交并核对直接依赖。其他候选不自动放行。小范围实现细化写入对应规格；重要成果或契约变化按需使用 Correct Course。完成历史不重置，不增加独立路线台账或审批状态。

## 后期学习层方向

学习层是主产品具备多类完整、稳定的配置、生成和虚拟 ECU 能力之后的方向，不随首个 CAN 关口或单项诊断能力交付。届时拟帮助具备基本编程能力的学习者从零理解 Classic，并在本产品的真实工作区练习当时已验证的配置与运行能力。初步边界是：独立学习页承载课程与关卡，导览进入同一配置工作区；只读模板复制成独立的真实 ARXML 教学工程，学习进度不改变项目配置；关卡通过取决于实际配置、构建或运行证据，不能由点击或模拟结果代替。不把未实现模块、实机或认证声明包装成可用课程。

学习层当前不进入功能开发队列。待 CAN、深入诊断、生命周期或虚拟 I/O 等多类工程场景形成已审的可用组合，且工作区操作与交接稳定时，再决定是否启动详细规划；不以模块数量或日期代替这一判断。届时须重新确定七项问题：知识路径、教材出处与权利边界、工作区导览及恢复、模板复制与项目隔离、真实行为检查点与进度模型、初中高级关卡矩阵，以及交付时点。原始问题保存在[学习层早期议题](../../docs/project/archive/autosar-learning/map.md)；这些议题是规划输入，不是另一套在运行的任务状态，也不表示已批准实施。准备实施时先用 BMad 细化 PRD、架构与 epic/story，并核对当时对应运行能力的验收证据。

近期可执行需求见 [PRD](prd.md)，跨层设计约束见 [架构](architecture.md)，任务状态以 BMad sprint 文件为准。研究和早期决策保存在[平台历史资料](../../docs/project/archive/autosar-platform/map.md)与[学习层历史资料](../../docs/project/archive/autosar-learning/map.md)，用于追溯依据，不再作为另一份当前规划。
