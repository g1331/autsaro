# Autosar Classic 产品简述

本产品面向集成 AUTOSAR Classic ECU 的使用者，交付可独立运行的 Classic 基础软件栈代码，以及配置、校验和代码生成工具。完整参考 ECU 的运行基础须先按所选 AUTOSAR 版次核定 OS 要求，再决定采用可合法交付的现有 AUTOSAR OS，或以外部内核实现并验证兼容层；通信、诊断及后续模块的 BSW 实现由本产品提供，不依赖另一套现成协议栈。使用者从新建配置或导入多文件 ARXML，到安全编辑、校验、生成可独立构建和运行的工程，并取得可复现的行为证据。Windows 虚拟 ECU 是早期验证目标；指定 MCU 是另行验证的实际交付目标。长期方向是逐阶段覆盖所选 Classic 版次中当前有效的运行模块与多个目标平台；这表示逐个验证明确的模块、配置和目标组合，不表示一个 ECU 同时启用全部模块，也不预设总工作量或发布日期。

主要使用者是 ECU 集成工程师和 BSW 开发者：他们需要把系统/ECU 配置、应用接口和目标环境接成可交付工程。产品维护通用 BSW 实现，按项目生成配置与必要接口/集成代码，并提供完整输入、产物、构建和行为证据；不以“生成源码占比”衡量质量，也不替使用者生成车辆功能算法。Vector MICROSAR Classic＋DaVinci Configurator、EB tresos AutoCore＋Studio 是产品形态的参照，不是当前功能或符合性声明。

## 完整产品的功能构成

1. **输入与建模：**接受所声明范围内的系统/ECU 描述、ECU Extract、BSW 模块描述与配置，以及应用 SWC 描述；支持新建、导入、引用/变体校验、安全编辑与可追溯的往返。当前主机子集远未覆盖这些输入类别，不能把一般 ARXML 导入能力等同于完整 ECU 工程输入。
2. **配置与生成工具：**呈现模块和跨模块依赖，校验参数及目标约束，生成实际需要的 BSW 配置、RTE/应用接口和目标集成文件；明确哪些产物是复用的栈源码、哪些按 ECU 生成，附构建与交接清单。
3. **可运行软件栈：**维护声明支持的通信（包括适用的网络管理）、诊断、系统、存储、I/O、安全等 Classic BSW 模块实现及其真实接口行为；以选定 OS/RTOS 与具体目标驱动形成可运行闭包。通用应用算法、芯片厂商专有驱动和未获权利的软件不默认为本产品自有实现。
4. **集成与证据：**支持独立构建、Windows 虚拟 ECU 验证和指定硬件目标验证，并对配置、目标、工具链、版本和适用规范义务出具可复现的成功、拒绝、恢复与未验证记录。

“完整产品”意味着上述链路能对声明支持的典型 ECU 工程从合法输入走到交付与复验，并持续扩大所选版次的适用模块与目标覆盖；它不是仅有配置编辑器、单条主机协议链，也不等于所有车辆应用、芯片驱动、版次和安全认证一次到位。各模块的完整支持配置及规范义务须经独立盘点和实证定义，当前尚无可据以宣布整体完成的单一百分比分母。

**已确认的第一条产品链：通用 CAN＋诊断参考 ECU。**它不承担某一车型或 T-Box 的专属业务：使用者给出受支持的 ECU/BSW 配置和一个示例 SWC 的接口描述，配置 CAN 信号收发与物理诊断连接，获得含自有 BSW、必要生成物、应用接口及目标依赖清单的独立工程；先在 Windows 虚拟目标、再在指定 MCU 上复现通信、诊断和故障恢复。示例应用只用于证明接口闭合，不构成车辆功能算法产品。具体输入格式、诊断服务子集、OS 实现和首块板卡仍须按规范、来源和验证成本收口；确认参考 ECU 不等于批准这些尚未定义的实现范围。

网络管理属于这条 CAN 参考 ECU 产品链的完整交付范围，须明确区分 ComM 的通信模式请求、Nm 通用接口、CanNm 总线专属状态机及 CanSM 控制器/总线状态管理。开发过程中可用“常开 CAN、无网络管理”的受限配置先验证通信与诊断，但不能以它作为首个完整参考 ECU 的退出结果。首个完整参考 ECU 应在声明的单 CAN 网络配置下验证请求/释放网络、NM PDU、睡眠/唤醒及异常恢复；主机 `STARTED/BUS_OFF` 切换或周期报文不能充当这些证据。部分网络、网关协调与其他总线 NM 留到相应配置和对端可验证时决定。

使用者应能从配置或真实 ARXML 输入，看到保存及生成差异，得到完整工程，离线构建、运行、复现成功与拒绝场景。无法安全保留的引用、影响生成的未知配置和未支持变体须明确拒绝。主机行为、内部已审支持、实机支持与公开发布是不同声明。

“完整”有两层验收口径：近期对每个声明支持的 ECU 配置，交付它运行所需的代码、配置、接口、目标适配和可复现行为闭环；长期逐步扩大所选 Classic 版次中当前有效运行模块的覆盖范围。当前已有 CAN 主机信号链和有界 DoCAN 行为；现有 `Os_Advance` 是虚拟时间调度器，尚未把这些 BSW 路径接到选定的 RTOS。已有实现与任务完成记录是起点，不能由历史任务数量推算 Classic 总完成率，也不能把单项 story 完成等同于产品阶段退出。以后每个受支持组合分别记录版次、配置、RTOS 及其适配、目标、工具链、规范义务和验收证据。

FreeRTOS 因维护者的既有经验、MIT 许可及 Windows 仿真路径，可作为早期集成与主机验证候选；这一候选尚未解决完整 Classic 参考 ECU 的 OS 要求。产品最终要对所声明的 AUTOSAR OS 可扩展性等级满足 R24-11 的配置、接口与运行义务：可评估以 FreeRTOS 为内核实现适配，或选择其他可合法交付的 AUTOSAR OS；两条路径均须逐项验证，不能把原生 FreeRTOS 任务调度或 `Os_Advance` 称为 AUTOSAR OS。选择具体实现及 MCU 端口后再固定版本与许可，不以未验证依赖填补工程。

现阶段产品类型和第一条参考工程方向已清晰，功能规格仍未完全收口。进入大规模模块开发前，需据 R24-11 方法学与 SWS 为该参考 ECU 建立输入/产物清单和模块依赖图；明确首个目标 MCU 的合法 MCAL/驱动来源；比较 FreeRTOS 适配与 AUTOSAR OS 要求之间的差距；以 Vector/EB 的公开工作流核对配置到交付的缺口。调研产物应是可审阅的产品范围、支持矩阵与技术决策，再进入 PRD/epic/story；未知标准义务不直接转成开发任务。

## 产品方向与阶段原则

- **当前基线：**以 CP/FO R24-11 的 Windows 主机 CAN／有界诊断行为收口输入、保存、生成、构建和正反向交接证据；它仍是虚拟目标，不因单项 story 完成而升级内部支持声明。
- **运行基础与 OS 契约闭环：**经规范和主机可行性核对后，FreeRTOS 可承载通信、诊断、网络管理的有界主机集成实验；首个完整参考 ECU 的阶段出口须另确定 AUTOSAR OS 实现路径、声明的扩展等级及其配置、任务/中断、计时与资源等适用证据。主机实验和现有虚拟时间调度不能充当 OS 规范出口。
- **首个 MCU 工程闭环：**选择具体芯片、板卡和工具链，在可获得的底层驱动与应用接口条件下，用同一受支持 BSW 子集构建、上板并验证。主机与实机分别验收，不以一次上板宣称普遍芯片支持。
- **扩展阶段：**先沿实际依赖深化诊断、持久存储、系统生命周期与 I/O，再扩其他网络和横向模块；每一增量交付端到端可运行的配置组合，逐步扩大 Classic 当前有效运行模块及目标范围，不用空接口代替运行能力。阶段按使用者能完成的工程闭环划分，模块是逐组合验收的支持范围。
- 完整参考 ECU 必须对其声明的 AUTOSAR OS 范围建立独立支持档案；若仅有 FreeRTOS 原生运行证据，只能声明有界的 Classic BSW 在该 RTOS 上运行，不能声明完整 Classic 平台。主机虚拟运行、指定芯片实机运行、第三方互操作、完整标准义务、功能安全和公开发布是不同的声明。Windows 运行可形成有边界的主机交付，但其调度和时间证据不能外推到硬件；取得板卡、合法工具及目标证据后，才为具体芯片和工具链建立实机档案。其他规范版次独立验证，不静默混版或迁移。
- Adaptive Platform 是单独的产品与部署方向。待多类 Classic 能力稳定、选定 AP 版次及真实模型和运行样本后再决定是否立项；不预造共用 CP/AP 模型或运行实现。
- 当前只在本地研发。开源是长期方向，发布许可、第三方权利、外部依赖和支持承诺在启动公开发布时单独核定；公开可读的规范和 XSD 不自动取得再分发权。

## 后期学习层方向

学习层是主产品具备多类完整、稳定的配置、生成和虚拟 ECU 能力之后的方向，不随首个 CAN 关口或单项诊断能力交付。届时拟帮助具备基本编程能力的学习者从零理解 Classic，并在本产品的真实工作区练习当时已验证的配置与运行能力。初步边界是：独立学习页承载课程与关卡，导览进入同一配置工作区；只读模板复制成独立的真实 ARXML 教学工程，学习进度不改变项目配置；关卡通过取决于实际配置、构建或运行证据，不能由点击或模拟结果代替。不把未实现模块、实机或认证声明包装成可用课程。

学习层当前不进入功能开发队列。待 CAN、深入诊断、生命周期或虚拟 I/O 等多类工程场景形成已审的可用组合，且工作区操作与交接稳定时，再决定是否启动详细规划；不以模块数量或日期代替这一判断。届时须重新确定七项问题：知识路径、教材出处与权利边界、工作区导览及恢复、模板复制与项目隔离、真实行为检查点与进度模型、初中高级关卡矩阵，以及交付时点。原始问题保存在[学习层早期议题](../../docs/project/archive/autosar-learning/map.md)；这些议题是规划输入，不是另一套在运行的任务状态，也不表示已批准实施。准备实施时先用 BMad 细化 PRD、架构与 epic/story，并核对当时对应运行能力的验收证据。

近期可执行需求见 [PRD](prd.md)，跨层设计约束见 [架构](architecture.md)，任务状态以 BMad sprint 文件为准。研究和早期决策保存在[平台历史资料](../../docs/project/archive/autosar-platform/map.md)与[学习层历史资料](../../docs/project/archive/autosar-learning/map.md)，用于追溯依据，不再作为另一份当前规划。
