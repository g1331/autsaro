# Autosar Classic 产品需求：已交付基线与滚动产品规划

本文供产品维护者、架构与实施规划使用。R1–R7 是当前 Windows 主机剖面的需求；FR-1–FR-15 定义完整参考 ECU 成果。维护者已确认 Epic 4 主路线为固定 FreeRTOS 内核＋自有 AUTOSAR OS 语义实现＋有限单核策略扩展，以单核 SC1 为目标并保持原生 Windows。路线已采用，Epic4已交付固定生产依赖，4.1～4.22全部完成；全部适用Win64主机SC1行为及工程交接已通过独立复验。主机SC1、集成与MCU分别依据实际结果核定；产品方向见[产品简述](product-brief.md)，后续Epic仍未启动。

本阶段收口现有主机剖面：使用者从受支持的配置输入取得可独立交接、构建和运行的 Windows 虚拟 ECU 工程，并复现双 ECU CAN 的正向、拒绝与恢复行为。该剖面为独立 Classic 基础软件栈提供输入、生成和行为基线；旧目标保留虚拟时间轮询；Epic4新目标通过独立FreeRTOS backend集成，实际范围由其故事结果确定。已有单项行为或 story 完成也不自动代表本阶段退出。

## 用户成果与边界

- R1：从 R24-11 多文件 ARXML 或工作台配置形成可检查的工程状态；保存与重开不得悄悄丢失引用或未支持内容。
- R2：确定性生成独立 C99 工程，完成主机 GCC 构建；其 CanIf→Can 信号收发及有界诊断按声明配置真实运行。
- R3：对不支持的版本、变体、引用、CAN ID、DLC、控制器状态和诊断输入提供可定位的拒绝结果，不输出假成功。
- R4：每项新能力交付输入、独立预期、实际正反向结果及适用规范出处；按相应 BMad story 的验证与复核确定完成，说明实际配置与目标范围。
- R5：面向使用者的进度须区分新增运行行为、操作和交付改进、仅证据进展，以及仍未验证的维度。
- R6：通过显式“导出可重建主机交付包”操作，对已保存且通过当前主机剖面校验的 R24-11 多文件 ARXML，交付工程须随附完整的输入快照、各文件原有逻辑身份、版次/工具版本及来源和完整性清单。另一位工程师在另行取得同版工作台及合法 R24-11 XSD 后，可从交付目录重新导入并再生成等价的 C99 工程；未保存、外部已改动、缺文件或引用不闭合时拒绝可重建交付，生成的清单与路径映射不写源机器绝对路径，且不额外打包密钥或运行状态；源 ARXML 原文由交付者审阅。
- R7：提供一组有独立预期的合法双 ECU 主机参考输入和离线复验入口。只用交付包、PowerShell、GCC 与独立测试器即可复现 CAN 正向报文、适用诊断及至少一条拒绝/恢复路径；缺少工具、文件损坏、报文不符或超时须给出失败结果，不把生成或构建成功显示为行为已验证。

**已交付的受限产品成果：Epic 3 主机工程交接。**当前源码与 story/sprint（提交 `817063e`）已包含可重建输入包、重新导入和离线参考复验入口；该完成记录限定于该 story 的实际功能。Epic4架构及22条故事已确认，开发与完成由其各自BMad规格／sprint记录。R6/R7 以及 R1–R5 的对应部分使用本仓库已支持的固定 11 位 Classical CAN、单虚拟控制器、当前有界物理 DoCAN 和 Windows/GCC 目标；参考输入由产品用现有工作台创建并校验。它交付可重建的主机工程及独立复验，不声称已接受完整 ECU Extract、BSW Delivered Bundle、SWC 描述，也不声称 RTE、AUTOSAR OS 或 MCU 已实现。R24-11 [Classic 方法学](https://www.autosar.org/fileadmin/standards/R24-11/CP/AUTOSAR_CP_TR_Methodology.pdf)的 ECU 配置输入要求因此保留在 FR-1 等完整参考 ECU 需求中，不由主机专属输入替代。此阶段不需要预选 OS 或购买板卡。

## 跨阶段的交付完整性

- 对每个拟声明的 ECU 配置，清单须分别指出产品维护的通用 BSW 代码、按该配置生成的代码与描述、使用者提供的应用、选定 RTOS 及合法目标驱动。生成源码占工程行数的比例不作为验收指标；缺少已声明场景必需的接口、符号、配置、构建或行为证据时，该组合不算完整交付。
- 支持声明须绑定 CP/FO 版次、模块及配置/变体、OS 实现与适配、目标/工具链，并按对应 BMad story 验证实际接口与行为。未启用模块不要求进入某个 ECU 的工程；目标目录的长期扩张不折算为未经定义的“符合 AUTOSAR 百分比”。
- 初期可评估 FreeRTOS 做有界集成与 Windows 主机验证；内核及端口版本、许可证随实际交付固定。完整参考 ECU 须对声明的 AUTOSAR OS 可扩展性等级满足适用的 R24-11 OS 配置、接口与运行义务，具体可评估 FreeRTOS 内核加经验证的兼容实现或另一款可合法交付的 AUTOSAR OS。原生 FreeRTOS 主机移植、固定 RTE 桥接及虚拟调度均不能推定这些义务通过，具体 MCU 仍须单独验证。

产品级功能规格仍待补齐：系统描述/ECU Extract、BSW 模块交付描述与 ECUC、SWC 描述的实际输入契约；模块依赖与变体边界；配置编辑/校验/生成、RTE、通用 BSW、OS/RTOS、MCAL/目标驱动及应用之间逐项可交付的责任；可复现的构建、主机和板级验收。各类输入不要求首个剖面一次全部支持，但每个对外声明的工程场景必须明确其必需输入和缺失时的拒绝。调研这些契约及 R24-11 适用规范后，先定首个典型 ECU 工程和支持矩阵，再把其缺口拆成开发任务。

## 下一产品增量：Configurator 与应用工程

长期候选范围以[产品简述](product-brief.md#长期候选路线)为唯一目录；本节记录已确认的近期用户要求，不改变 R1–R7、FR-1–FR-15 的历史编号和已完成范围。R5／R6 是路线候选 ID，不是本文的主机需求 R5／R6，也不是正式实施 Epic ID。2026-10-03 用户确认界面与图标暂定基线，并授权完成 R5 需求、增量架构、故事拆分和就绪检查；本轮不编码。以下 R5 需求已收口，是否进入实施由选定范围的就绪结论决定，不由全局 draft 或原型完成自动推定。

- **CFG-1 独立配置主流程：**使用者无需官方 XSD／MOD 档案、编译器、Rust、Node、uv 或源码 checkout，即可用交付工作台完成声明支持的工程新建／模板／导入、检查、编辑、保存、校验和源码生成。标准结构、模块参数与跨模块规则由软件实现；编译与虚拟运行是可选操作，缺少执行工具只影响这些操作。
- **CFG-2 统一工程操作：**不同真实工程在同一工作区和权威模型中提供工程／模块／容器／对象导航、参数编辑、引用选择及跳转、搜索、批量修改、问题定位、保存及变更／生成预览。无效引用、未知生成语义与外部变更明确定位；不以只能改参考样例几个参数作为完成。
- **CFG-3 版次与依赖管理：**软件随包提供版本化的内置校验规则和自有 BSW 模块定义，呈现版次、规则版本、身份、覆盖与实际校验结果；正常配置不要求用户下载或指定官方 XSD／MOD。第三方模块定义可显式导入为隔离扩展，不替换内置规则、不自动增加生成支持。官方资料是研发核对与独立对照验证的输入，不默认获得再分发授权。
- **CFG-4 产物所有权：**应用源码、产品通用 BSW、生成配置／RTE 与目标文件责任明确；重复保存和生成保留用户拥有的代码，交接不依赖修改生成器或每次复制后手改协议栈。生成规则、升级及迁移边界在近期架构中确定。
- **APP-1 应用结构：**工程可表达 SWC 类型与实例、组合、端口／接口／数据类型、S/R 与 C/S 连接、ECU 映射，以及 runnable／event／周期与任务映射。扩展哪些队列、模式与异步机制在具体剖面中决定，不把它们混成一种通信语义，也不推迟到多核阶段。
- **APP-2 生成与运行一致性：**所选应用组合形成一致的 RTE／SchM、应用接口和 OS 配置；非法类型、连接与调度关系在生成前可定位。应用开发者实现明确接口，产品不生成车辆功能算法。开发验收仍须独立编译、链接和行为复验，不能用“配置不需要编译器”免除生成／运行质量责任。

R5 复用 Epic 4 的输入、生成计划、OS、后台状态与交接基础，不另建配置体系或调度器。视觉依据为[根 DESIGN.md](../../DESIGN.md)，交互依据为[暂定 EXPERIENCE.md](ux-designs/ux-Autosar-2026-10-03/EXPERIENCE.md)。这份 UX 描述当前剖面迁移；其中标为 FUTURE 的通用参数、结构与批量编辑由下述需求正式纳入 R5，但静态原型不作为其实现证据。R6 的 APP-1／APP-2 仅共同固定对象及源码所有权接缝，不在 R5 实现多组件连接或新调度语义。

### R5 选定范围与完成契约

**产品成果：**集成工程师安装软件后，用内置规则与自有模块定义建立、打开并修改不同实际 ECU 工程，检查参数及引用、保存可重开的原始配置，预览并交接声明支持的源码；不需要官方 XSD／MOD、作者 checkout 或预先安装编译器。不是把固定样例的几个字段换成新外观。

**输入与支持边界：**CP R24-11，现有 CAN 信号输入、已有标准 ECU Extract 多文件输入，以及由内置自有模块定义或显式接受的同版第三方定义解释的 ECUC 配置值输入。自有模块的定义覆盖全部已声明配置，而不是只内置几个表单字段。模块／容器浏览和定义驱动配置编辑不等于该模块已有运行时生成器；生成闭包仍限于已实现 CAN 主机与标准 ECU 集成剖面，Windows／Linux 受控目标分别取证。未知定义、未选择变体、不能安全往返或不能解释的生成语义须可见，保留有效未知内容，不静默忽略或扩大声明。

**2026-10-03 内置规则修订：**用户确认把校验规则直接实现进软件，替换正常配置链对外部官方档案的依赖。此要求尚未实施；现有 `Workspace` 仍读取外部 Schema，历史 Epic 1／3／4 的证据及旧交接契约不重写。内置规则须独立实现 XML 结构／顺序／基数／类型、自有模块参数／引用及既有目标的跨模块规则，并在研发阶段与合法持有的固定官方资料和独立正反例对照验证。把官方原文压缩、加密或自动转换成代码不作为绕过权利核定的方式。

**CFG-1.1 工程生命周期。**无需配置官方档案或执行工具即可进入工作台，选择并检查合法路径的多文件输入、查看实际原文与结构诊断。声明支持的输入由随包内置规则校验，显示实际执行范围及结果；规则已安装不等于校验已执行。非良构 XML、DTD／实体、危险路径拒绝，未覆盖规则不得标为通过。导入不覆盖当前未处理草稿或原文件；内置规则缺失或损坏是软件安装／工具错误，不要求用户补找 XSD／MOD。

**CFG-1.2 新建与模板。**提供产品原创的空 CAN 工程、可生成 CAN 信号工程和已有标准 ECU 示例模板；模板声明版次、内置规则身份和目标，真实创建到用户选定空目录，预览文件后确认，不覆盖现有内容、不包含官方原件或个人路径。模板与声明支持的配置在无官方档案、无编译器的离线环境中可校验及准备源码；空 CAN 工程仍遵守既有无信号拒绝生成边界。更改工程名、帧／信号或合法参数后走同一模型，不依赖手改生成器。

**CFG-1.3 打开与重开。**工程成员、配置剖面及明确接纳的第三方定义身份可在重启／搬移后恢复；成员信息仅记录源成员和接纳身份，不复制参数、定义正文或通过状态。重开核对精确原字节定义，缺失／损坏仅限制其消费者，不默选其他版本或机器全局定义。未建立工程成员文件的直接 ARXML 会话不隐式恢复扩展选择，可明确“保存为工程”保留当前接纳集合，成员与源配置同一预览／保存事务。普通多文件选择、原主机与标准 ECU 交接入口保留真实输入和各自完整性验证，不用 JSON 元数据替代源文件或依赖核对。

**CFG-2.1 对象与文件导航。**实际工程／模块／容器／参数／引用具有源文件归属与稳定身份；选择、表格、检查器、问题定位及关系跳转共用这一身份。重复显示名、改名和跨文件引用不能定位错对象。搜索覆盖名称、完整路径、定义路径及参数值，作用域明确；筛选不能丢失选择或草稿。原文只读查看来自实际输入，不读任意工程之外路径。

**CFG-2.2 定义驱动编辑。**在已绑定且支持的定义／变体中，整数、浮点、布尔、枚举、字符串、函数名及引用采用类型合适的编辑器，呈现单位、范围、枚举、基数和默认值来源；未落盘默认值不能悄悄变成显式配置。未知类型、未支持的表达式或变化条件只读说明，不从当前 VALUE 猜类型。应用校核范围、基数、引用目标类型和涉及对象关系；错误留在原字段，内存工程不部分修改。

**CFG-2.3 引用与结构。**候选目标来自同一真实工程及定义的合法目标集合；可跳转到源／目标，未解析或错误 DEST 有定位诊断。支持定义允许的模块／容器实例创建、改名、移除及参数／引用条目修改；改名更新实际入站引用，移除有引用对象时须预览并在同一批次重定向／移除引用，否则拒绝。不能靠字符串全局替换、不默认删除未知内容；SWC 连接／映射的新增语义仍属 R6。

**CFG-2.4 批量修改。**多对象修改先展示对象、文件、旧值／新值与影响关系，按一个输入身份全部应用或全部拒绝；重复目标、互相冲突、越界、失效身份与未知可写性不能产生部分应用。已有无关问题应可继续定位修复，不能因尚未支持的生成语义阻断所有安全配置修正；新引入的类型／结构／引用错误须拒绝。

**CFG-2.5 保存与问题恢复。**应用只改变内存，预览不写盘，确认保存才改原配置。未修改文件逐字节不变，有效未知内容保留；外部修改、同一路径歧义、待恢复备份或失效预览拒绝写入并保留原文件。问题携带 severity、code、message、remedy、源文件及可解析对象／字段。保存执行实际可核定的内置结构与定义约束；未覆盖内容明确标为未支持／只读或目标阻断，不借缺官方档案跳过已支持规则。源安全保存、规则校验与目标生成分开，修复后的错误消失不等于整个工程通过。

**CFG-3.1 规则与能力。**软件提供内置结构校验代码、自有模块定义及跨模块规则，以 `RuleSetIdentity={release,rulesVersion,sha256}` 标识产品规则实现／清单，不用官方档案摘要冒充软件规则身份。设置只读显示内置版次与覆盖，普通用户不选择 XSD／MOD 路径。第三方定义导入核对版次、来源、摘要及冲突，不允许覆盖自有定义或内置规则；未支持表达式、变体或运行语义准确拒绝／只读，不能从定义存在推定生成支持。缺扩展只限制依赖它的对象；缺编译器只限制原生预检／构建／运行，不能关掉整个工作台。

**CFG-3.2 失效与设置。**内置规则身份随软件版本确定，不由用户路径或 XSD／MOD 环境覆盖替换；升级规则或成功变更扩展定义、目标、工具时，按真实依赖使校验、预览及下游结果失效并保留草稿。失败保存保持旧设置与工程。外观、规则与模块定义、执行工具分别提交，内置覆盖只读，扩展导入／移除显式确认；执行工具环境覆盖仍优先且不写回。浅深／系统主题持久保存，同一车身与透明轮廓随有效主题切换灯位，主题不改变配置或结果归属。

**CFG-4.1 独立源码准备。**已保存且满足所选剖面闭包的配置可在无编译器时预览源码、差异、文件归属、目标和依赖清单，再显式确认写入独立目录。未知消费参数、未闭合引用、未选择变体或缺少生产者的接口阻断该目标，不输出空壳。生成、编译预检、构建、主机行为均独立，不继承旧通过或运行旧二进制。

**CFG-4.2 用户代码与再生成。**区分配置、用户应用、产品通用 BSW、生成配置／RTE、目标和构建文件。用户应用仅在显式初始化时建立，不在再生成中覆盖；已被用户修改的生成文件与旧版清单冲突须列出并拒绝，而非强行恢复。新增／移除生成文件及升级必须预览并确认拥有权，失败保留旧有效产物；工程搬移、重开与再次生成不要求手改生成器或复制协议栈。

### R5 验收与质量边界

- **CFG-NFR-1 数据完整性：**成功往返与关键拒绝均通过真实磁盘文件验证；比较未改文件原字节、受影响字段与引用、失败前后输入集合和旧产物，不以 UI 回显证明安全。
- **CFG-NFR-2 所有权与并发：**单一后台 Session、单一前台工作台状态、输入身份绑定的预览／应用／结果；切换工程、取消、资源变化及晚到结果不污染新上下文。取消确认以前不得声称进程已经关闭。
- **CFG-NFR-3 桌面可用性：**落实暂定 UX 的统一菜单／工具轨／树表检查器／工具窗口、草稿保护、问题焦点接力、快捷键、字段 label／错误关联及对话框焦点；1080×720 可完成主链，窄屏仅为阅读回退。颜色／图标不单独承担状态信息，正式安装图标与原型身份一致。
- **CFG-NFR-4 分发与复验：**Windows 和 Linux 在隔离原生环境中证明：无网络、无官方 XSD／MOD 文件及对应路径／环境变量、checkout 不存在、无 Node/Rust/uv/编译工具，仍可新建／导入、定义编辑、保存重开、真实校验与源码生成。声明支持的规则须在研发阶段对照固定官方参考校验和独立正反例，发现差异必须解释并修正规则或明确未覆盖，不能弱化有效拒绝以制造通过。生成源码另由独立消费者用锁定工具构建及复验行为；macOS 无隔离宿主仍如实未验证。
- **CFG-NFR-5 性能与受限输入：**继承输入大小／路径／XML 安全限制；解析、规则／定义索引、校验和全文扫描不占 GUI 主线程。过滤和展开复用按输入、内置规则及扩展身份绑定的快照索引，不重复读源或加载定义；长期任务可取消，错误显示有界且可复制完整 owned 日志。

**退出场景，全部必要：**

1. 两个名称、帧布局和参数不同的原创 CAN 工程从新建／模板进入真实模型，执行对象及引用编辑、批量修正、保存重开、内置规则校验和源码交接。全链无官方档案、网络或编译器，再由独立消费者构建并比较实际 CAN 行为。
2. 原创七文件标准 ECU 输入及其不同 ID／周期变体在无官方档案的同一壳层中校验并生成，保持应用／类型／映射只读边界及安全编辑；保存、搬移交接、再生成和原有 CAN／DID／拒绝恢复复验不回退。R5 新交接记录产品规则及所需扩展身份；旧格式仍按自身来源与完整性契约分派，不替换历史摘要或自动放宽闭包。
3. 内置自有模块定义驱动不同 ECUC 模块／嵌套容器配置，真实呈现并编辑多种参数与跨文件引用，测试默认值、重复名称、基数、创建／改名／有引用移除及全拒绝批次；不能只用固定 CAN 表单证明通用编辑。显式第三方定义扩展另验错版次、冲突和未知语义；无该模块生成器仍拒绝目标生成，安全保存与浏览不受无关扩展缺失阻断。
4. 无官方档案与执行工具时默认支持链可用；内置规则缺失／损坏、未覆盖输入、错误扩展身份、外部改源、目录冲突、旧预览、用户代码改动、取消及晚回调均保留输入／旧输出并给出实际原因。研发用官方模型只作为合法的独立浏览／保留项与对照验证输入，不因打开成功就宣称可生成或全量官方 Schema 通过。

**不在 R5 新增的能力：**R6 多 SWC 连接／调度、R7 扩大诊断故障、R8 网络管理、MCU、Adaptive、其他 AUTOSAR 版次、全局历史 Undo／Redo、跨重启草稿恢复或认证。现有能力照常迁移，不删减；这些边界不取消候选路线或完整参考 ECU 的后续义务。

**术语：**工程是被明确选定的源文件集合与配置剖面；对象是其中可定位的实际实例，不是显示名；定义描述可核定配置约束，不自动提供运行语义；草稿、已应用配置、已保存输入和生成产物分属不同所有权。输入角色与产物归属不由文件名后缀猜测。

## 历史 Epic 2 的诊断需求承接

接收范围为[候选 R7：可配置 CAN 诊断与故障工程](product-brief.md#r7)，具体迁移记录见[epics 的诊断承接契约](epics.md#diagnostic-carryover)。历史 Epic 2／Story 2.1 不再独立实施；规划合并不表示代码实现或验收完成。

- **DIAG-1 独立故障：**至少两个不同 DTC／事件与其受支持监测源可配置、保存重开并形成完整生成工程；单个故障的触发、恢复或清除不能错误改变另一个。事件—DTC 是否一对一须按所选 SWS／ECUC 明确，不从旧实现猜测。
- **DIAG-2 诊断一致性：**对承接的 `0x19/0x01` 数量、`0x19/0x02` 列表及适用读取／清除操作，结果与实际事件及状态掩码一致；分别触发和同时触发有独立预期。不将“请求成功”当作故障状态正确。
- **DIAG-3 持久恢复：**每个故障按配置保存、重启恢复和清除；存储损坏、写入失败或配置不匹配可观察，不伪装为空故障或成功清除。主机跨进程恢复不代替真实 Flash 证据。
- **DIAG-4 拒绝边界：**重复 DTC、无效监测引用、不支持的诊断子功能，以及超出声明容量的输入在适当边界明确拒绝；保留安全的原输入／产物。旧 Story 的“最多两个、第三个拒绝”属于原剖面边界；新剖面以两个作为最小隔离验收，实际容量和上限拒绝经设计确定，不默认永久限制为两个。

R7 正式化时须将 DIAG-1–DIAG-4 分配到实际 Story 并双向引用历史 2.1；所选 R24-11 Dem／Dcm／NvM 及 ECUC 对象、适用条款、容量与独立报文预期在编码前核定。继承现有有界行为，不单独扩充旧模型后再另做一次标准集成。

## 首个参考 ECU 的功能需求

目标使用者是 ECU 集成工程师：他应能将系统/ECU 描述、一个示例 SWC、产品 BSW 及选定目标环境组合成工程，交给另一位工程师独立构建和验证。下列 FR 规定产品行为与验收结果，不预设所有源码均由生成器写出。每个 FR 的可实施配置、适用规范条款、输入样例与拒绝样例须在相应 epic/story 中进一步限定；在缺少目标选择时，不能据此直接开始板级实现。

**UJ-1 参考 ECU 交接：**一位 ECU 集成工程师导入所需描述、查看并修正配置阻断，生成含应用接口和完整依赖清单的工程；另一位工程师按清单构建 Windows 与指定板级目标，用独立 CAN 对端和诊断测试器验证信号、DTC 与网络睡眠/唤醒，随后重启复验持久状态。遇到不支持的变体、断开的引用或目标证据不足时，工作台指出阻断原因，工程师保留原输入及旧产物，不会误认交付完成。

本文的“完整参考 ECU”指 FR-1–FR-15 在一个声明的 R24-11 单 CAN 配置与指定目标上形成输入、生成、运行和证据闭环；“产品长期完整性”指持续扩大所选 Classic 版次的适用模块及目标组合，不用一个参考工程代替全部模块范围。Nm 是通用网络管理接口，CanNm 是 CAN 网络管理实现，ComM 管理通信使用者请求，CanSM 协调 CAN 总线模式；它们不能用 Can 控制器状态 API 互相替代。

| 参考工程要素 | 责任与交付口径 |
| --- | --- |
| 系统描述/ECU Extract | 实际项目由使用者提供；产品为参考 ECU 自行维护一份合法、可复验的样例，工具只接受声明支持的输入/派生路径 |
| BSW 模块描述与通用代码 | 产品为自有 BSW 实现维护与生成其所需描述、配置规则及源码，不借用另一套商业 BSW 栈 |
| ECUC 配置值 | 使用者在工作台建立或导入；工具校验来源、跨模块引用和所选目标闭包，并输出可追溯配置 |
| SWC 描述与应用代码 | 参考 ECU 由产品提供最小示例；实际车辆功能由使用者提供，产品只保证声明支持的接口集成路径 |
| RTE/BSW 调度与生成配置 | 产品按受支持的 SWC、ECU 与 BSW 描述生成，并随工程交付接口及构建清单 |
| OS 实现、MCAL/目标驱动 | 依适用 AUTOSAR OS 规范选择并验证实现；外部软件须注明版本和许可；产品负责适配、配置、集成与可验证闭包，不默认取得第三方再分发权 |

### 输入、配置与交接

- **FR-1 工程输入：**使用者可为声明支持的 R24-11 参考 ECU 导入或建立 ECU Extract、ECUC、所需 BSW 模块描述和至少一个 SWC 描述及其映射。工具逐项显示必需、可选与外部提供的输入及来源；缺少影响工程闭包的输入时不能生成完整工程。当前工作台对多文件 ARXML 的支持不等于这些输入类型均已实现。
- **FR-2 安全编辑：**使用者可检查并修改受支持的 ECU 参数，预览受影响文件；未修改文件和未支持但有效的无关内容保持原样。引用、变体或来源并发变化使保存不安全时，操作须拒绝并指出受影响对象，不产生静默丢失或未经确认的迁移。
- **FR-3 配置闭包：**工具对所选 CAN、诊断、网络管理、RTE、OS/RTOS 和目标适配参数及跨模块引用给出可定位校验结果。必需配置、引用或变体未闭合时拒绝该目标生成；拒绝信息区分输入问题、未支持范围和工具错误。
- **FR-4 产物交接：**每个受支持组合交付可复现的源文件/生成文件清单、版本与来源、配置、外部依赖、构建方法和已验证场景。另一位工程师无需仓库内隐含文件或手工补符号，即可按清单构建；无法满足时不能称该组合已完整交付。

### 应用接口与运行基础

- **FR-5 SWC/RTE 集成：**对声明支持的一个示例 SWC，产品从其接口和 ECU 映射得到必要的 RTE/BSW 调度与接口产物，使应用调用、BSW 服务和构建链接闭合。验收至少包含应用值进入发送链、接收值回到应用、错误接口/映射被拒绝；固定主机 `Rte_ReadSignal`/`Rte_WriteSignal` 不构成通过。
- **FR-6 OS 运行与声明：**完整参考 ECU 应按选定的 R24-11 AUTOSAR OS 可扩展性等级生成/接受 OS 配置，使适用任务、ISR、计数器/告警、调度表、事件、资源及启动/关闭行为与 BSW/RTE 调度闭合，并逐项验证该等级的接口与运行义务。底层内核可以另选，但仅验证原生 FreeRTOS 任务调度不满足此 FR；在 OS 规范证据完成前，交付与界面只能称其为有界 BSW-on-RTOS 剖面。
- **FR-7 目标驱动：**在选定 MCU/板卡/工具链及合法驱动组合上，工程能构建和链接，真实 CAN 控制器与适用存储/唤醒路径可运行；目标差异及外部驱动责任列于交接清单。主机虚拟驱动的结果不得用于替代此目标验收。

### 单 CAN 网络的通信、诊断与网络管理

- **FR-8 CAN 信号链：**声明支持的单 CAN 网络可按合法配置收发、打包/解包和传递应用信号，并对错误 ID、DLC、方向、控制器状态与超时给出可复验的拒绝或无效状态。主机和实机分别保留独立预期报文与结果。
- **FR-9 物理诊断连接：**外部测试器可在声明的一条物理 CAN 诊断连接上完成受支持的 DoCAN 传输及已列明的 UDS 服务/子功能；首个参考配置至少覆盖会话切换、读取一个应用 DID、读取与清除一个受监测 DTC。未声明的 SID、子功能、会话与寻址方式按适用协议拒绝，不得从当前主机单项行为推定完整 UDS 支持。
- **FR-10 故障与持久状态：**一个明确的监测源可驱动受支持 DTC 状态，并在所选目标的真实存储路径上按声明策略保存、重启后恢复和清除。存储损坏、失败或配置不匹配时不得伪装为空故障；主机文件 NvM 只作为主机证据。
- **FR-11 单网络管理：**在声明的单 CAN 网络管理配置中，通信使用者可请求与释放网络，ComM、Nm、CanNm、CanSM 与底层 CAN 的模式及回调形成闭环；对端可观察 NM PDU、网络运行、准备睡眠、睡眠和唤醒。错误模式、丢帧、bus-off 或唤醒失败应有可观察状态和恢复/拒绝结果。常开 CAN 可用于中间开发，但不满足首个完整参考 ECU 的此项验收。

### 验证、证据与声明

- **FR-12 主机验证：**另一执行者可用 Windows 虚拟 ECU 和独立对端重建受支持配置，检查输入往返、工程生成/构建、应用通信、诊断、网络请求/释放及故障恢复；结果标明主机时间与硬件行为的界限。
- **FR-13 实机验证：**在选定板卡和真实对端上，另一执行者可重建同一声明范围的应用通信、诊断、网络管理、重启及适用故障路径；保留实际构建/链接、报文、时序、资源、存储与中断证据。缺少目标证据时仅保留主机声明。
- **FR-14 支持矩阵：**产品对每个版次、模块/服务、配置/变体、RTOS、目标和工具链组合显示“已实现的有界行为、未实现或不支持”的实际依据；状态反映实际构建和行为结果，不维护额外审批档案。
- **FR-15 失败关闭：**输入不完整、生成/构建失败或行为证据未通过时，保存可定位错误和可恢复的既有输入/产物，不把旧构建或部分结果标为新配置的完成交付。

首个完整参考 ECU 只覆盖一个明确的 R24-11 单 CAN 网络、一个示例 SWC、选定诊断与 DTC 配置、一个板级目标及一个已声明并验证的 AUTOSAR OS 可扩展性等级；它的完成不能代替其他 CAN 变体、全部 UDS 服务、部分网络/网关协调、其他总线、所有 MCU 或更高 OS 可扩展性等级的支持声明。长期产品继续按依赖扩大有效 Classic 模块覆盖，并逐组合验收；该范围不被首个参考 ECU 的边界取消。

**PM 提议的首个参考配置：**一个 11 位 Classical CAN 网络、一条物理 normal-addressing DoCAN 连接、一个示例 SWC 和应用 DID、一个带持久状态的受监测 DTC；诊断服务从现有主机子集的 `0x10`、`0x3E`、`0x22`、`0x19/0x01`、`0x19/0x02`、`0x19/0x0A` 与 `0x14` 核对适用标准后收口。单网络管理优先评估 ComM `FULL` 与主动 CanNm 的基础配置，暂不引入部分网络或网关协调；该选择能验证 ECU 主动保持网络与协同释放网络，符合[ComM 变体定义](https://www.autosar.org/fileadmin/standards/R24-11/CP/AUTOSAR_CP_SWS_COMManager.pdf)中的功能边界。FreeRTOS 可用于前期主机实验，[官方许可](https://freertos.org/libraries/license.html)为 MIT；完整参考 ECU 路线已确定为 FreeRTOS＋自有 OS 语义＋有限单核策略扩展，目标单核 SC1；等级能力不能由实验推定。该段是待规范/目标复核的产品剖面提议，不把现有主机回调或计时参数自动升级为标准实现。

1. **输入基线：**首个参考工程采用哪份可合法使用的 R24-11 ECU Extract/BSW 描述/SWC 样例，哪些描述由产品提供、哪些由使用者提供？退出物：可追溯的输入清单与至少一组正反例。
2. **诊断与 NM 剖面：**首个完整支持矩阵的 UDS SID/子功能、DTC/存储策略、单网络 CanNm 变体与计时参数是什么？退出物：按适用 SWS/ECUC 明确的配置与独立预期，不把主机自有行为当成全部标准语义。
3. **AUTOSAR OS 技术闭合：**实现选择已确定为固定 FreeRTOS＋自有 AUTOSAR OS 语义＋有限单核策略扩展，目标单核 SC1，保持原生 Windows。按 R24-11 [OS 规范](https://www.autosar.org/fileadmin/standards/R24-11/CP/AUTOSAR_CP_SWS_OS.pdf)及 OSEK 完整义务建立配置、调度、接口、栈和错误证据；生产版本/补丁/端口组合固定，主机和 MCU 独立取证。Epic4已完成对应实现及逐故事验证，4.22已独立复验全部适用Win64主机SC1行为与工程交接；任意用户工程仍须复验其实际配置。交付：实际 SC1 接口和行为、固定依赖与许可、可独立构建和复验的工程。开发和验证记录按 BMad，不增加矩阵或独立验收报告；普通缺口不重新打开选型。
4. **首个硬件目标：**用户目前没有开发板。PM 推荐以 NXP [FRDM-A-S32K344](https://www.nxp.com/design/design-center/development-boards-and-designs/FRDM-A-S32K344) 为首个评估候选：官方列出板载 CAN FD、S32 Design Studio 和可用于 AUTOSAR/非 AUTOSAR 的 RTD；[NXP 指南](https://www.nxp.com/document/guide/s32k344-evb-quick-start-guides%3AGS-S32K344-WB)列出 S32K344 的 Can RTD 示例。购买或绑定为产品目标前，须实际核对可取得的 RTD/FreeRTOS/工具链版本及许可、CAN 收发器/存储/唤醒路径和真实对端。[NXP 的公开技术答复](https://community.nxp.com/t5/S32K/S32K356-RTD%E9%80%89%E6%8B%A9/m-p/2402912/highlight/true)将可见的 RTD 6.0.0 对应 R21-11、7.0.1 对应 R23-11；尚无由此可推定的 R24-11 ECUC 或接口兼容性。退出物：固定版本、合法来源、构建和对端路径的目标档案；评估不通过则重新选板。

当前声明仅限 CP/FO R24-11、Windows 虚拟 ECU、本地 GCC 和各具体功能所声明的有界配置。旧目标`Os_Advance`是主机虚拟时间调度；Epic4新目标独立交付固定FreeRTOS、汽车OS语义和真实栈适配，完整主机等级依据4.22实际复验。真实 MCU、第三方互操作、完整 MISRA、功能安全、官方一致性及公开发布不包含在本阶段的通过声明内。
