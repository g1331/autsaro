# Epic 9：运行时、生成 C 与开发工程体系整顿

## Why

后续功能将持续修改现有运行时和代码生成链。开发者需要清楚的模块责任、可靠的标准契约和容易定位问题的测试，避免小改动牵动大量源码、只能等待整套验证才能发现错误。Epic 9 在 R11 消费者实施前整理全部现有交付，关闭适用的软件标准差距，并以正常开发入口和持续源码门禁保护后续修改。需求来自 PRD QLT-1–QLT-5；本规格完成表示整理任务的约束已明确，不表示整改完成或 Story ready-for-dev。

## Capabilities

- **CAP-1**
  - **intent:** 模块开发者依据完整公共契约和明确状态责任维护已交付运行时及直接依赖。
  - **success:** 对支持配置的接口、类型、配置语义、状态、错误、回调、描述和适用内存映射逐项核定，适用软件差距关闭；独立接口与成功、拒绝、恢复向量在对应 Windows/Linux 目标成立。
- **CAP-2**
  - **intent:** 生成器开发者从一致来源维护并生成可独立接手的工程，保留旧工程和用户源码。
  - **success:** 每份受影响产物的来源与唯一生产者明确，重新生成后实际编译、链接和运行闭合；配置往返、确定性、用户源码、旧封存完整性及必要显式迁移有回归证据。
- **CAP-3**
  - **intent:** 维护者明确代码规范的实际适用范围，消除真实违反并完成自动工具不能替代的人工检查。
  - **success:** 固定 MISRA 221 项均有范围内适用性及必要自动／人工依据；诊断的真实违反、误报、不适用与未知分开，采用代码责任已核定，真实违反关闭；未核查或无法消除项继续阻塞对应出口。
- **CAP-4**
  - **intent:** 开发者用项目正常入口快速验证修改，并能找到失败原因，减少后续开发的重复劳动。
  - **success:** 生成配置、运行时行为、共享类型／接口三类改动有清楚的修改落点、最小有效检查与完整验证升级条件；记录可比开发反馈耗时和重复工作，旧行为及独立风险覆盖保留，受影响真实原生操作按隔离条件验证。
- **CAP-5**
  - **intent:** 团队在可解释的 CI 成本下获得每次 PR 的严格源码保护。
  - **success:** 双目标完整样本与实际程序每轮重新生成分析，严格结果进入必需聚合与分支保护；违规、漏扫、工具失败、必需任务跳过／取消的实际 PR 不能合并；可比完整运行分别核定门禁新增成本与优化收益。
- **CAP-6**
  - **intent:** 独立接收者能够从新目录正常复验整理后的工程，再供后续功能使用。
  - **success:** 非实现者完成配置往返、新目录生成、独立构建、主机行为与失败恢复、旧工程／用户源码和离线交接复验；全部整改、必要人工评估、兼容审阅和严格门禁通过后才关闭 Epic 9 并放行 R11 消费者实施。

## Constraints

- 完整范围覆盖 legacy、单组件、多组件及 Windows/Linux 受控目标：自有 runtime、生成 C、Rust 渲染／模板、配置模型／内置定义、共享类型、ABI／清单、离线工具及固定内核／port／patch 直接依赖；六个 CI 样本不代替全部已支持配置。
- 固定 CP/FO R24-11、MISRA C:2012 Third Edition＋AMD1–AMD4＋TC1–TC2、C99；逐角色核定义务，合法原文缺失阻塞相应裁决。Mandatory 不允许偏离；无法消除的真实违反保持阻塞，本轮不批准任何偏离、规则降级或批量 suppression。
- 继承 Epic 9 AD-1–AD-8 及其父约束，原 ID 保持；唯一配置权威、验证计划、运行状态所有者和调度 backend，不以目录合并抹掉不同 profile 的契约。
- 标准公共面、模块私有面、主机／测试控制分离；跨模块类型、回调与配置衔接只定义一个生产者；生成修复回到实际来源，迁移同步所有调用方、配置、资产与验收。
- 保留安全保存、create-only 初始化、live／sealed 分离、预览确认失效、所有权和旧封存完整性；公开签名、布局、句柄语义或交接格式变化先审阅兼容影响与必要显式版本迁移，资产摘要不构成授权。
- 普通配置和源码生成继续不依赖官方档案、编译器或网络；研发标准依据与真实目标构建前置条件分别核对。采用现有 npm、Cargo、uv、autosar_tooling、ecu-tool 与 Actions，不新增代理专用系统或通用生成框架。
- 标准预期独立于被测实现与 ABI 清单；按实际程序边界检查源码，不丢平台／配置／失败覆盖，不缓存扫描通过结果；工具可用、扫描完整、源码通过、人工评估和实际行为分别证明。
- 研究／设计可按实际依赖先行；实施进入须满足对应模块资料、独立预期、共享契约和兼容审阅，最终出口另需严格门禁及独立复验。具体条件见 work-packages.md。

## Non-goals

- 不实现 MCU、新 CAN 类型／通道、完整 NM／CanSM、未选可选变体，不重选 OS／技术栈或重设计界面；已支持配置的适用软件义务仍在范围内。
- 不将安装包、公开发行、真实硬实时、ASIL 或认证由主机结果推定通过；受影响原生行为仍须验证。
- 本轮不实施重构、不创建正式 Story／stories.yaml、不变更 sprint 状态、不修改 CI／保护规则，不以未知诊断数生成任务。

## Success signal

开发者能按正常入口修改一个已支持模块，只在清楚的责任范围内同步源码、生成来源和消费者，及时得到有意义的失败反馈；独立接收者在新目录通过完整工程复验，严格 PR 源码门持续阻止回归。该结果须同时满足 CAP-1–CAP-6，规划定稿或单层通过不能代替。

## Assumptions

- 具体文件粒度沿已采用架构的待审结构建议，由模块契约细化后确定；不预定全仓搬迁或新的 ABI 版本。

## Open Questions

- **Q1：**各模块合法固定规范与 MISRA 授权正文从哪里取得，如何核定摘要和适用条款？未满足前不得关闭对应标准裁决。
- **Q2：**确需改变公开契约时，哪些调用者和旧工程受影响，采用兼容适配还是新版本／显式迁移？对应实施前完成审阅与授权。
- **Q3：**当前诊断哪些是真实违反，221 项人工评估及采用代码问题怎样逐模块关闭？未知保持未知，不能直接折算成任务或通过。
- **Q4：**哪些生成／构建／检查阶段占据实际开发等待，哪些优化有可比收益，严格必需门是否真正阻断？沿现有日志和正常入口实测后确认，不预承诺降幅。
