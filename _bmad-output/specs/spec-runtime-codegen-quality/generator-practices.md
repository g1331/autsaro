# 代码生成软件的开发与维护实践

本材料把成熟工具的官方经验落实到 Epic 9 的开发负担问题。资料于 2026-10-10 阅读；这是工程方法依据，不是 AUTOSAR／MISRA 条款，也不是引入这些工具的决定。架构不变，采用方式受 Epic 9 AD-1–AD-8 约束。

## 生成阶段清楚，业务判断不藏在文本里

MLIR 将处理组织为明确的 pass，并支持保存失败输入与 pipeline 信息用于复现。本项目借鉴阶段边界和失败定位：保留“源解析／引用→语义校验→不可变计划→模块产物→封存”，将类型、句柄、时序和配置语义在计划中决定，emitter 只表达已核定结果。失败诊断沿现有 PlanDiagnostic／日志记录阶段、源对象和产物来源；需要复现的输入使用既有 fixture／私有失败现场，不新增常驻跟踪或报告系统。[MLIR Pass Infrastructure](https://mlir.llvm.org/docs/PassManagement/)

**对后续修改的要求：**修改某模块配置规则应有明确的校验落点和 emitter，不能在多个模板／C 字符串替换中各写一次判断。跨模块 callback／共享类型的唯一生产者先由共同契约固定；不引入 MLIR、通用 pass manager、第二种持久化中间模型或插件框架。

## 生成文件和手写文件分开负责

Xtext 提供专门的生成输出位置，将全派生文件与可编辑源码区分，并把校验分成语法、引用和自定义约束，支持不同成本的检查时机。本项目采用责任分离与成本分层，但不照搬其生成目录自动删除方式：现有 live 应用源、sealed 输出、所有权和完整性拒绝更严格，继续保护。普通编辑反馈、保存安全检查、生成前完整语义校验和后续真实构建各有作用；便宜检查不替代必需约束。[Xtext Language Implementation](https://eclipse.dev/Xtext/documentation/303_runtime_concepts.html)

**对后续修改的要求：**生成器不要求开发者手改生成 C 来修产品缺陷；算法源码继续由用户维护。生成路径变化同步资产映射和封存工具，不把规则身份／输入指纹不匹配当成“重新生成即可覆盖”。不引入 Xtext／EMF／Java，也不为模板替换新增依赖。

## 小反例快速查错，完整工程证明效果

LLVM 区分单元、小回归与完整程序测试；小回归集中在单个特性或最小缺陷输入。rustc 分开 check、build、run 的通过／失败预期。本项目借鉴这些层次：源语义拒绝用最小 ARXML／计划反例，emitter 用局部结构断言，公共 ABI 用独立 C consumer 编译链接，owner／计时／协议用实际目标行为，交付再做新目录独立接收。[LLVM Testing Guide](https://llvm.org/docs/TestingGuide.html)、[rustc UI tests](https://rustc-dev-guide.rust-lang.org/tests/ui.html)

**对后续修改的要求：**不要让每个细小错误只能靠整套 CI 或 GUI 才发现。局部测试断言与契约有关的符号、类型、次序或拒绝，不固定整个生成包的大段文本。只有字节本身属于 seal／确定性契约时才比较完整字节。不能批量更新快照吸收错误；LLVM 的自动生成检查经验不用于本项目唯一标准预期，标准及行为预期仍从独立原文／向量定义。不新增 lit／FileCheck／compiletest，复用现有 Cargo 与 Python suites。

## 缓存先证明失效正确，再谈增量速度

rustc 的 query 按键返回结果，重复请求复用缓存，并追踪依赖支撑可靠的增量计算。本项目据此选择先减少重复解析／校验／组装，复用已有不可变计划、fingerprint、可信资产和 Cargo／依赖缓存；不立即开发通用持久 query 引擎。[rustc Queries](https://rustc-dev-guide.rust-lang.org/query.html)

**对后续修改的要求：**局部缓存只有测到热点后才设计，必须覆盖源字节、规则／定义、profile/target、应用快照与生产者身份等实际依赖。用修改输入、外部源码变动、规则变化、目标切换和冷／暖路径等价反例验证失效；缓存不能让旧确认发布新结果。编译中间物缓存不等于本轮生成／源码分析结果，完整样本仍每轮重生成分析。并行只处理独立只读产物，最终按稳定顺序组装并拒绝 producer 碰撞。

## 开发负担要测，不能只量 CI 总时间

Cargo 提供按测试目标／名字选择运行及构建耗时报告。项目使用锁定工具链支持的现有命令和 CI／进程日志区分等待来源：依赖准备、Rust 编译、生成、C 编译／链接、分析、行为和平台准备。`--timings` 等现有选项只在适用入口诊断，不新增团队必经 profiler。[Cargo test](https://doc.rust-lang.org/cargo/commands/cargo-test.html)、[Cargo build timings](https://doc.rust-lang.org/cargo/reference/timings.html)

效率验收采用三类代表性实际改动，结果写到对应 Story，而非新建 benchmark 台账：

| 改动 | 应能定位的范围与快速反馈 | 完整验证仍须覆盖 |
| --- | --- | --- |
| 一个模块的生成配置规则 | 输入规则／plan／模块 emitter及直接消费者；最小有效正反配置、局部产物与接口编译 | 受影响 profile、目标、实际 main、运行及 seal／交接 |
| 一个 runtime 状态／错误行为 | 模块 owner 与直接上下层；独立状态机／恢复向量 | 并发、真实执行与生成工程旧行为，受影响平台原语 |
| 一个共享类型／公开接口 | 唯一 producer、所有声明／调用方与映射；独立 compile/link consumer | 全部受影响配置、程序与 ABI／旧包兼容，必要原生操作 |

每类记录实际必须修改的位置、最快有意义反馈的命令与耗时、失败定位是否清楚、需要升级完整验证的理由；在可比环境分别观察首次和重复执行。优化前后解释减少了哪些重复工作、哪些新检查增加了成本，不预设任意文件数／分钟／百分比门槛。若拆分新增重复配置、多处语义解释或更多无必要入口，应回到现有责任边界简化。快速反馈改进不允许削弱标准、数据保护和完整退出。
